## 0. 产品形态前提（第一性约束，先于一切需求）

> **本节是所有需求的解释框架。任何与本节冲突的需求描述，以本节为准。**

### 0.1 OneDesktop 是「1 个人 × N 个 Agent」的单机应用

| 维度 | OneDesktop | 竞品（AgentTeams / AgentSpace / Coze / Relevance） |
|------|-----------|--------------------------------------------------|
| 人类参与者 | **恰好 1 个**（本机使用者） | N 个（团队成员、多租户） |
| 协作对象 | 人 ↔ Agent、Agent ↔ Agent | 人 ↔ 人、人 ↔ Agent、Agent ↔ Agent |
| 状态归属 | 本机 SQLite，**无服务端** | 中心化数据库 / K8s 集群 |
| 账号体系 | **无**（不需要登录） | 必需（OAuth / RBAC / 租户） |
| 进程边界 | 单进程 + 子进程（CLI 执行器） | 跨主机、跨容器 |

**"群协作"在本产品中的准确含义是：一个人指挥多个 Agent，不是多个人一起干活。**
所谓"群"是**上下文隔离与并行执行的组织单位**，借用了 IM 的界面隐喻，但**不存在第二个人类**。

### 0.2 由此确定不需要做的整类能力（不是"暂缓"，是"永不"）

账号/登录、多租户、RBAC 权限层级、成员邀请、在线状态、@人通知、消息已读回执、跨端消息同步、并发编辑冲突解决（人与人的）、服务端消息路由、席位归属权转移、审计的"操作人"维度。

> 这类需求若出现在后续迭代提案中，应直接以本节为由驳回，无需二次论证。

### 0.3 但「单机」≠「离线」——仍然依赖网络的三处

1. **LLM API 调用**（DeepSeek / OpenAI）——核心链路必须联网。
2. **远程 MCP Server**（HTTP transport）——R1 打通后可能连外部服务，凭证管理与网络失败处理仍是必需项。
3. **CLI 执行器内部的网络行为**（codex / claude 等子进程自行联网）。

因此：**网络错误处理、超时、重试、离线降级提示仍在范围内**；但**"多端同步 / 服务端状态一致性"不在范围内**。

### 0.4 单机形态带来的三项结构性红利（应主动利用，而非仅仅"接受限制"）

| 红利 | 具体含义 | 对本 PRD 的影响 |
|------|---------|----------------|
| **零部署门槛** | 双击即用，从安装到第一次多 Agent 协作可做到 < 60s | R7 单聊升级为群之所以成立的根因；竞品需要建租户/建 CRD |
| **全量本地上下文** | Agent 直读本机文件系统，无需上传/同步/授权流转 | Agent 间共享用**文件路径**而非消息体传大内容（§9 已写）；F10 并行隔离只需处理 Agent×Agent 冲突，**无人×人冲突，复杂度低一个量级** |
| **数据零外传** | 除 LLM API 必要请求外，全部状态留在本机 | 隐私敏感场景（法务/财务/医疗/涉密）的**唯一可选形态**；也决定了指标不能靠云端埋点（见 §2.0） |

## TL;DR（给高管的一页纸）

**产品定性（先于一切）**：OneDesktop 是**「1 个人 × N 个 Agent」的单机应用**，不是团队协作软件。竞品解决"多人一起干活"，我们解决"一个人指挥一支 Agent 队伍"。详见 §0。

**一句话**：OneDesktop 的群协作"骨架已立、血肉未填"——Agent 有席位、能扇出、能竞速，但**工具生态没打通、过程看不见、Worker 被阉割成只读**。本 PRD 只解决一件事：**让群协作"能用、敢用、会用"**。

**只能做三件事（互相无依赖，可并行）**：
1. **MCP 打通**（F1）：把外部工具生态接进来。这是能力矩阵里唯一"人人都有、只有我们没有"的项，投入产出比全表最高。
2. **运行记账 + 席位仪表**（F3 + IX-1/IX-2）：现在 metrics 是内存计数器、重启即丢。先把"谁在干什么、花了多少 token、多少钱"落库并可视化——用户看不见就不会信任，就不会把重要任务交给它。
3. **Worker 审批冒泡**（F2 + IX-5）：现在 Worker 的 Ask 因无审批 UI 退化成 Deny，群内 shell/memory 工具被直接砍掉。补全四态审批（accept/edit/respond/ignore），尤其 `edit`（改参数放行）价值最高。

**第四件（采用率关键）**：**单聊一键升级为群**（IX-15）。当前"先建群才能说话"在信息最少时收最重的决策税。改成"聊着聊着一键升级"，直接解决"群协作建了没人用"。**这是竞品结构上做不了的一条**——AgentTeams 的 Team 是 K8s CRD，AgentSpace 的工作区是多租户实体，都不可能从一次对话里长出来。

**战略边界（三条不要走的岔路）**：不追治理深度（RBAC/多租户/零信任网关）、不引常驻服务依赖（Matrix/MinIO/PostgreSQL）、不把"更像组织"当目标（席位是上下文隔离单元，不是真部门）。OneDesktop 的护城河是**单机原生、零基础设施、单人开箱即用**。

**预期收益**：群任务端到端可观测；Worker 工具能力从"残"变"全"；协作采用率因升级路径而提升。所有指标见 §2。

## 1. 问题陈述（Problem Statement / Why）

### 1.1 现状（代码级盘点，事实性）

后端骨架（v1.0 圆桌 + M1/M2/P2 改造）已落地：圆桌双模式（扇出 `post()` / 竞速 `broadcast()`）、`WorkerPool` 派活与 DAG 依赖、`AgentProfile` 定义、`ToolRegistry` 多态执行器、`CliExecutor`（codex/opencode/pi/claude）、`auto_approve_override` 防挂死、`roundtable_alternatives` 存竞速落选、trace_id 链路、三态权限矩阵。

**但四类硬缺口让协作"形同残废"**：

1. **工具生态断在探活层**：`mcp/client.rs` 只做 `initialize → tools/list → resources/list → prompts/list` 握手，**全仓无 `tools/call` 路径**。Agent 被锁死在内置 filesystem/shell/memory 三类工具，席位再多也无米下锅。
2. **运行期不可见、不可信**：`telemetry/metrics.rs` 只有内存 `AtomicU64`，**不持久化、无 per-conversation 成本、无 trace 树、无回放**。用户看不到 Agent 在干什么。
3. **Worker 被阉割成只读**：三态权限矩阵已有，但 Worker 会话的 Ask **因无审批 UI 退化成 Deny**；群路径为避免挂死统一 `auto_approve_override: Some(true)`。等于"全放行"与"全拒绝"二选一——`run_shell`/`update_memory` 默认 Deny，工具能力缺席。
4. **协作入口门槛错配**：必须先建群、配席位、写任务卡，才能说第一句话。真实场景几乎总是"单聊聊着聊着发现一个 Agent 干不完"。

### 1.2 竞争坐标（客观）

- **方向正确，但赛道已不空**（结论一，已下修）：2026-06 起阿里 **AgentTeams**（K8s CRD + Matrix + 零信任网关）与港大 **AgentSpace**（数字员工 + AgentRouter 多 harness 归一化 + 审批/预算/看板）密集入场，组织建模比 OneDesktop 更完整。
- **剩余独占位 = 单机原生桌面、零基础设施、单人开箱即用**。两者本质是企业多租户服务端治理平台；OneDesktop 假设"一个人 + 一台电脑"。
- **短板不在架构在交互层**（结论二）：运行期可见性与可干预性是所有"组织隐喻派"产品的共同软肋，也是 Claude Code Teams / Devin / CrewAI Traces / LangGraph Studio 的体验壁垒——这正是我们要补的。

> 竞品对标细节见 §6；完整差距清单（F1–F14、IX-1–IX-17）见依据报告 §5/§6。

## 2. 目标与成功指标

### 2.1 产品目标

- **G1（能用）**：Agent 能调用外部 MCP 工具，不再受限于三类内置工具。
- **G2（敢用）**：用户能实时看见每个席位的运行状态、耗时、token、成本；Worker 调危险工具会冒泡审批且可改参数放行。
- **G3（会用）**：用户能在单聊中途一键升级为群，上下文不丢；竞速落选方案可见、可改选。

### 2.0 单机产品的指标前提（必须先读）

**没有服务端 = 没有全量埋点。** 因此本产品的指标分成性质完全不同的两类，不可混为一谈：

| 类别 | 采集方式 | 谁看 | 能否设"全网目标值" |
|------|---------|------|------------------|
| **A 类·本机运行指标** | R2 落 SQLite，本机可查 | **用户自己**（R4/R5 面板） | 否——每台机器一份，不聚合 |
| **B 类·产品决策指标** | ① dogfooding 本机数据 ② 用户主动反馈 ③ **可选**匿名遥测（默认关闭） | PM / 开发 | 仅在样本内有效，须标注样本来源 |

**明确决策：本发布不做默认开启的遥测上报。** 理由：§0.4「数据零外传」是护城河的一部分，为了几个数字破坏它不划算。B 类指标在 M2 阶段**只以 dogfooding 样本（开发者本机 + 内测机器）为准**，样本量小、结论仅作方向参考，**不作为发布门槛**。

> 若后续确需遥测，须满足：默认关闭 + 首启显式询问 + 仅上报聚合计数（无会话内容/无文件路径/无 prompt）+ 可随时关闭并删除本地队列。作为独立提案评审，不在本 PRD 内。

### 2.1 北极星指标（North Star）

> **WACS — 本机周活跃多 Agent 协作会话数**：一周内"发生过 ≥2 个 Worker 实际执行（含由单聊升级而来的群）"的会话数。
> 它同时捕捉"协作是否被真正用起来"与"IX-15 升级路径的采用率"，是 G1–G3 的综合信号。

- **性质**：B 类（决策指标），**单机口径**——统计的是"一台机器上"的协作活跃度，不是全网用户数。
- **基线**：上线前无法观测（无 `runs` 表）。
- **目标（dogfooding 口径）**：上线第 4 周，**内测机器人均 WACS ≥ 3**（即平均每周至少 3 次真正用上多 Agent）。
  - ⚠️ 前版写"WACS ≥ 50"是 SaaS 全网口径，**单机形态下不可采集，已作废**。
- **判定成功的替代信号**（更适合单机产品）：内测用户中"**升级为群后没有退回单聊**"的比例 ≥ 60%。

### 2.2 A 类·本机运行指标（用户自己看，R4/R5 面板呈现）

这类指标的价值是**建立用户对 Agent 的信任**，不是给 PM 汇报。目标值由用户自行判断，产品只负责准确呈现。

| ID | 指标 | 呈现位置 |
|----|------|---------|
| A1 | 本轮/本群 total & prompt & completion tokens、请求数、总耗时、预估成本 | R5 摘要条 |
| A2 | 每席位当前状态、本次耗时、token、累计成本、历史成功率 | R4 席位卡片 |
| A3 | 任务级并行度（甘特条是否重叠） | R5 时间线 |
| A4 | 审批历史（工具、参数、决策、来源、耗时） | R3 审计回看 |

### 2.3 B 类·驱动指标（dogfooding 样本，方向参考）

| ID | 指标 | 基线 | 目标 | 采集 |
|----|------|------|------|------|
| D1 | 群工具调用成功率（成功/总调用） | ≈0%（Worker 工具被 Deny） | ≥ 95% | 本机 `run_steps` 可算，**技术性指标，样本无关** |
| D2 | 审批响应时延（Ask 冒泡→用户响应，P50） | 不可观测 | < 60s | 本机可算 |
| D3 | MCP 工具可用率（已配置 server 中可 `tools/call` 比例） | 0% | 100% | 本机可算，**技术性指标** |
| D4 | 单聊→群 升级使用率（有入口曝光的会话中实际点击比例） | 无入口 | dogfooding 样本 ≥ 15% | 样本内，方向参考 |
| D5 | 竞速备选查看率（有落选方案的轮次中展开对比比例） | 0%（未暴露） | dogfooding 样本 ≥ 30% | 样本内，方向参考 |

> **D1/D3 是技术性指标**（"能不能用"），本机自测即可判定，不受样本量影响，**可作为发布门槛**。
> **D2/D4/D5 是行为性指标**（"用不用"），单机下无全网数据，**只作方向参考，不作发布门槛**。

### 2.4 健康指标（Health / Guardrails，本机实时生效）

| ID | 指标 | 警戒线 | 触发动作 |
|----|------|--------|---------|
| H1 | 单 Worker 平均 token/任务（按单价折 ¥） | 用户可配阈值 | 超阈值自动转审批（见 R3/R7） |
| H2 | 审批拒绝率（拒绝/总审批） | > 40% | 提示"默认权限可能过严，建议下调 Ask 范围" |
| H3 | 群协作会话异常终止率（崩溃/挂死/未释放） | 0 | 发布阻断项 |
| H4 | 工具调用超时率 | < 5% | 发布阻断项 |

> 健康指标是**本机护栏**（运行时直接干预用户当前会话），不是汇报数字——这是单机产品的优势：指标即刻可作用于本地行为，无需等待云端聚合。
> 所有基线须在 R2（运行记账）上线后 2 周内以 dogfooding 样本完成首次校准，写回本表并标注样本量。

### 3.2 Out of Scope / Non-Goals

> **首先适用 §0.2 的整类排除**（账号/多租户/RBAC/成员/在线状态/@人通知/消息路由/操作人审计等——因"只有一个人"而结构上不成立的能力）。本节列出的是**在此之上**的额外边界。

**战略边界（三条不要走的岔路，来自结论四 + §9）**：
- **NG-S1 不在治理深度上追赶**：不建 RBAC / 多租户 / 零信任网关 / L1-L3 人类权限层级。单人场景下这些是纯负担；只需"我知道 Agent 干了什么、能拦下它"。
- **NG-S2 不引入常驻服务依赖**：不引 Matrix homeserver / MinIO / PostgreSQL / AI 网关。现有 SQLite + Tauri Event 已够支撑单机多 Agent；每加一个依赖就把"双击运行"变成"先读部署文档"。
- **NG-S3 不把"更像组织"当目标**：席位是**上下文隔离单元**（Manus 教训），不是真部门。不为了角色完整性加用户不会配的 TeamAdmin 层。

**明确不做（来自 §9 反面教训）**：
- **NG1** 不做可视化画布编辑器（OpenAI Agent Builder 2026-11-30 关停；定义靠表单，画布只做只读渲染见 M3 的 IX-12）。
- **NG2** 不让执行 Agent 自维护 todo 文件（Manus 实测 1/3 动作耗在更新 todo；任务状态由 `TaskScheduler` 系统托管，保持）。
- **NG3** 不无限扩充单 Agent 可选动作（Copilot Studio 阈值 30–40；MCP 打通后须按席位做工具白名单）。

**推迟到后续发布（M3/M4，本 PRD 仅登记、不展开）**：
- M3：F12 通信拓扑策略、F5 Worker 间通信、F6 任务心跳防死锁、F7 结构化黑板、F4 Manifest 导入、F8 Skill 三级预算、F11 CLI 诊断、IX-3/6/7/16。
- M4：F9 Playbook、F10 并行隔离/变更集、F13 凭证边界、F14 记忆分层、IX-10/11/12/13/14/17。

## 4. 需求详述

### R1 · MCP 工具打通（F1）

**用户故事**：作为用户，我希望给某个席位接入一个已配置的 MCP Server 的真实工具（如查数据库、调内部 API），以便 Worker 不再只会读写文件和跑 shell。

**业务依据**：能力矩阵唯一"人人有、我们没有"项；Agent 被锁死在三类内置工具是协作价值的上限封顶。投入产出比全表最高。

**功能需求**：
- FR1.1 在 `ToolRegistry` 注册 MCP 工具，实现 `ExecutableTool` 的 MCP 适配器；接通 `tools/call` 全链路（含参数 schema 校验、结果回写）。
- FR1.2 多 Server 聚合时**客户端自加前缀消歧**：`mcp__<server>__<tool>`，兼容 Claude Code 授权匹配语法。
- FR1.3 **协议错误 ≠ 工具执行错误**：工具执行失败走 `isError=true` 把内容喂回模型自愈，不当异常抛。
- FR1.4 每次调用实现超时 + `notifications/cancelled`（复用 P0-4 异步工具取消机制）。
- FR1.5 tools list 加缓存层，为 2026-07-28 规范的 `subscriptions/listen` + `ttlMs` 预留接口。
- FR1.6 在 `capabilities_block()` 注入席位可用的 MCP 工具；按席位做工具白名单（呼应 NG3）。

**非功能**：MCP 规范按 `2025-06-18` 打底 + `2025-11-25` 增强；`sampling/roots/logging` 已 Deprecated（SEP-2577），**不新建实现**；tool annotations 视为不可信，`destructiveHint` 默认 true，仅用于降级默认策略。

**验收标准**：
- [ ] 配置一个含 ≥1 工具的 MCP Server，席位能在群内成功 `tools/call` 并返回结果。
- [ ] 两个 Server 有同名工具时，调用准确命中带前缀的那一个，无歧义。
- [ ] 工具执行报错时，Agent 能在不中断循环的前提下自愈重试或换路。
- [ ] 调用超时触发 `cancelled` 且会话不挂死。

**落点**：`src-tauri/src/mcp/client.rs`、`agent/tool_registry.rs`、`agent/tools/mod.rs`、`group/agent_profile.rs`。

### R2 · 运行记账与成本持久化（F3）

**用户故事**：作为用户，我希望每次群任务结束后能查到"这轮花了多少 token、多少钱、哪个 Worker 最慢"，以便评估值不值、并在下次前预估成本。

**业务依据**：R3/R4/R5/R6/IX-11 全部依赖这份数据——它是底座而非叶子。报告建议**从 P2-11 升为 P0 并前移**。

**功能需求**：
- FR2.1 新增 `runs` 表：group / task / worker / 起止时间 / stop_reason（复用 `AgentRunOutcome`）/ prompt&completion tokens / 预估成本。
- FR2.2 新增 `run_steps` 表：工具名 / 入参摘要 / 耗时 / 成功失败 / **审批决策**（accept/edit/respond/ignore）+ **审批来源** `human | auto_approve | timeout_deny`。
  - ⚠️ 单机单人，**不存在"谁批的"维度**——人类只有一个。需要区分的是"这次是人批的、还是自动放行的、还是超时兜底拒的"，这才是排查时真正要看的信息。
- FR2.3 成本用 `provider × model` 单价表本地换算（单价表可配置，初始内置 DeepSeek/OpenAI 常见模型）。
- FR2.4 引擎在 agent loop 关键节点写 run/step；崩溃可恢复（沿用 messages 逐条落库纪律）。
- FR2.5 提供查询 API：按 group / task / worker / 时间窗聚合。

**非功能**：SQLite 现有连接（WAL）；写入走既有 Repository 模式；单连接全局串行已在 P1-8 治理项关注，本需求不引入新连接。

**验收标准**：
- [ ] 一轮三 Worker 扇出结束后，`runs` 有 3 行、`run_steps` 含每个工具调用，token/成本可查。
- [ ] 重启应用后历史 run 数据仍在（不再内存丢失）。
- [ ] 成本 = Σ(token × 单价) 与 provider 账单误差 < 5%。

**落点**：`telemetry/metrics.rs`、`storage/connection.rs`、`agent/engine.rs`。

### R3 · Worker HITL 冒泡 + 四态审批卡片（F2 + IX-5）

**用户故事**：作为用户，我希望 Worker 想执行一个危险操作（如删文件、跑 shell）时，请求**直接弹到我眼前**，我能**改个参数就放行**或**给句反馈让它换做法**，而不是只能"批准/拒绝"导致它干不了活。

**业务依据**：当前 Worker Ask 退化为 Deny，群工具能力被阉割；`edit` 一态（改参数放行）是当前完全缺失、价值最高的一态（Claude Code `PreToolUse` 用 `updatedInput` 改写参数后放行是同一思路）。

**功能需求**：
- FR3.1 把 Worker 的 Ask 冒泡到**当前主窗口**，UI 标明"Worker X 请求执行 Y（工具名 + 参数）"。
  - **单机简化**：无需消息路由、无需收件箱、无需"批给谁"——唯一的人类就在屏幕前。竞品（AgentTeams 冒泡到 Lead 的 Matrix 房间、AgentSpace 走 runtime grants）必须做寻址，我们直接走 Tauri Event 推到前端即可。**这是实现上省掉的一整层。**
  - 但必须解决单机特有的问题：**用户可能没在看这个窗口**。须支持系统托盘/Dock 角标提示，以及"待处理审批"聚合入口（避免多个 Worker 同时 Ask 时前一个被后一个覆盖）。
- FR3.2 审批契约升级为 LangGraph Agent Inbox schema：`config{allow_accept, allow_edit, allow_respond, allow_ignore}` 决定渲染哪几个按钮；响应 `accept/edit/respond/ignore`。
- FR3.3 **`edit` 态**：参数可内联编辑后放行（尤其 shell 命令场景——路径写错改一下即可）。
- FR3.4 四项全 false 时默认允许 `ignore` 防卡死；按 tool annotation 分级设 TTL（`readOnlyHint` 长、`destructiveHint` 短），**超时默认 Deny（fail-closed）**并写入审计。
- FR3.5 审批决策落 `run_steps`（呼应 R2），支持审计回看。
- FR3.6 外部 CLI 席位的权限请求也走此冒泡（F11 的 tool approval bridge），不让外部席位成权限黑洞。

**非功能**：风险等级由 MCP `destructiveHint`/`readOnlyHint` 推导并在卡片展示；超时倒计时进度条。

**验收标准**：
- [ ] Worker 调 `run_shell` 时，主窗口弹出审批卡片，非 Deny。
- [ ] 应用未聚焦时，托盘/Dock 出现待处理审批提示；多个 Worker 同时 Ask 时不互相覆盖。
- [ ] 点击 `edit` 修改命令参数后放行，Worker 用新参数执行成功。
- [ ] 超时未响应自动 Deny 并落审计；四项全 false 时不卡死。
- [ ] 审批记录可在运行视图回看。

**落点**：`agent/permission.rs`、`agent/engine.rs`（`auto_approve_override` 处）、`group/roundtable.rs`、前端 `ProcessPanel.tsx` + 新审批组件。

### R4 · 席位运行仪表（IX-1）

**用户故事**：作为用户，我希望在群成员列表里直接看到每个席位"现在在干嘛、这次花了多少"，以便一眼判断谁卡住了、谁最贵。

**功能需求**：
- FR4.1 席位卡片从静态名片升级为运行仪表：当前状态（空闲 / 思考中 / 调工具 `<ToolName>` / 等审批 / 失败）、本次任务耗时与 token、历史成功率、累计成本。
- FR4.2 状态文案具体到工具名（"正在运行 `run_shell`" 远胜 "处理中"）。
- FR4.3 数据来自 R2 的 `runs` 表，实时随事件刷新。

**验收标准**：
- [ ] 一轮扇出中，三个席位卡片分别实时显示各自状态/耗时/token/成本。
- [ ] 状态文案含具体工具名。

**落点**：`GroupsPage.tsx`（席位列表）、`ProcessPanel.tsx`、事件订阅（统一事件总线）。

### R5 · 运行摘要条 + 甘特时间线（IX-2）

**用户故事**：作为用户，我希望群详情里有个"运行"视图，顶部一条总成本、下面一张任务时间线，以便一眼看出并行度到底用没用上。

**功能需求**：
- FR5.1 群详情新增第四视图"运行"，与 chat / dispatch / deliverables 并列。

- FR5.4 并行度可视化：若三个 Worker 的条形错位而非重叠，说明扇出未生效（这一洞察聊天流永远看不出）。

**验收标准**：
- [ ] 群详情出现"运行"视图，摘要条数值与 `runs` 一致。
- [ ] 甘特图正确展示 ≥2 个 Worker 的时间重叠。

### R6 · 竞速备选并排对比（IX-9）

**用户故事**：作为用户，我希望竞速轮次里能看到落选 Worker 的方案，并能一键改选，以便不浪费已经算出来的好答案。

**业务依据**：全篇性价比最高——`roundtable_alternatives` 已存落选方案，前端完全没暴露，只差一个 UI。横向看"多方案并排择优"是竞品空白区，是 OneDesktop 差异化资产。

**验收标准**：

### R7 · 单聊一键升级为群（IX-15）

**用户故事**：作为用户，我希望在普通对话聊到一半时，点一下"升级为协作群"，系统根据已有对话**预填建议席位与任务拆解**，我只需增删改就能开始协作——而不是从零建群。

**业务依据**：当前"先建群才能说话"在信息最少时收最重决策税；真实场景几乎总是单聊聊着聊着才发现一个 Agent 干不完。**这是全表唯一竞品结构上无法跟进的改动**（AgentTeams Team 是 K8s CRD，AgentSpace 工作区是多租户实体，都不可能从一次对话长出来）——恰好是单机形态的结构性优势。

**功能需求**：
- FR7.1 普通会话工具条加"升级为协作群"入口。
- FR7.2 点击后：① 当前会话完整上下文作为群初始共享状态（复用 `build_worker_seed`）；② 一次 LLM 调用按对话**预填建议席位 + 任务拆解**，用户只增删改；③ 原会话**原地转为群视图**，历史消息原样保留、不新建会话不搬迁数据（单机同库，纯本地事务，无跨服务一致性问题）。
- FR7.3 反向可走通：群任务收尾后可"折叠回单聊"，只留结论与产出物。
- FR7.4 结合 R2，升级时给出**事前成本预估**（呼应 IX-11，M2 至少做基础版：预估调用次数/大致 token）。

**验收标准**：
- [ ] 单聊中点升级，历史消息不丢，原地切到群视图（不新建会话、不搬迁数据）。
- [ ] 系统基于对话预填 ≥1 个建议席位与任务，可编辑。
- [ ] 群收尾后可折叠回单聊并保留结论。

**落点**：`chat-area`（工具条）、`group/roundtable.rs`（`build_worker_seed`）、`GroupsPage.tsx`。

## 5. 竞品对标（客观，不佐证自嗨）

| 维度 | OneDesktop（本 PRD 后） | 阿里 AgentTeams | 港大 AgentSpace | 启示 |
|------|------------------------|-----------------|-----------------|------|
| **人类参与者** | **恰好 1 人**（1人 × N Agent） | N 人（Human CRD / L1-L3 层级） | N 人（多租户 + 成员角色） | **根本分野**：它们解决「团队协作」，我们解决「一个人指挥一支队伍」——不是同一个问题 |
| 基础设施假设 | 单机、双击运行、SQLite | Docker+Matrix+MinIO+Higress / K8s | Node24+PostgreSQL+Google 登录 | **我们赢在门槛**，不在这三项深度 |
| 工具生态 | R1 后打通 MCP | MCP + 内部服务账号 | 多 harness CLI | 接入即追平"人人有"底线 |
| 运行期可见性 | R2/R4/R5 补齐 | 有（Trace 按 Team/Agent/Model） | 有（诊断维度+看板） | 我们补的是它们已有的，但**零部署**优势仍在 |
| Worker 审批 | R3 四态冒泡（推到唯一窗口） | Teammate 冒泡到 Lead（需寻址到人） | runtime grants + 审批 | 语义同构但**我们省掉整个路由层**——不用决定"批给谁" |
| 单聊→群 | **R7（独家）** | 不可（CRD 重资源） | 不可（多租户实体） | **结构性差异化，必做** |
| 治理深度 | 不做（NG-S1） | L1-L3 + 零信任 | 多租户+RBAC+OAuth | 单人场景是负担，不追 |
| 数据出域 | 仅 LLM API 必要请求 | 中心化存储 + 网关 | 服务端 PG + Google 授权 | 隐私敏感场景我们是**唯一可选项** |

> 我们不试图在"企业治理"上赢 AgentTeams/AgentSpace；我们在"单人零部署 + 可平滑升级 + 本地优先"上建立它们结构上做不到的体验。
>
> **判断竞品功能是否值得抄的一条判据**：如果这个功能存在的理由是"因为有第二个人"（成员管理、权限层级、消息路由、归属转移、操作人审计），那它对我们**结构上无意义**，不是"以后再做"，是"永远不做"（见 §0.2）。

## 7. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| R1 MCP 规范快速演进（2026-07-28 破坏性变更） | 适配器返工 | 按 2025-06-18 打底，缓存层预留 `subscriptions/listen`；不实现 Deprecated 的 sampling/roots |
| R3 审批弹出过多（一轮扇出 5–8 个）成新瓶颈 | 体验回退 | M3 的 IX-17 键盘快循环 + "本轮全部批准" + "此工具本次会话不再问"；M2 先保证不卡死 |
| R2 单价表不准导致成本失真 | 信任受损 | 单价表可配置 + 误差告警；明确标注"预估" |
| R7 预填席位质量差 | 用户仍从头填 | LLM 预填仅作建议，允许一键清空；降级为"空群 + 历史上下文"仍可用 |
| 多 Worker 并发写同 workspace 互相覆盖 | 数据损坏 | F10（M4）根治；M2 阶段沿用 `resolve_fs_path` 越界防护 + 任务卡声明文件范围（轻量）。**单机红利**：只需处理 Agent×Agent 冲突，无人×人并发编辑，可用本地文件锁而非分布式锁 |
| **单机特有 · 用户不在屏幕前**，Worker 审批无人响应 | 群任务静默停滞 | R3 的 FR3.1：托盘/Dock 角标 + 待处理审批聚合入口 + FR3.4 超时 fail-closed。**竞品可以推 IM 通知给同事代批，我们没有这个退路，必须靠本机通知做好** |
| **单机 ≠ 离线**：LLM API / 远程 MCP 断网 | 协作中断且状态不明 | 网络失败须与工具执行失败区分（呼应 FR1.3）；断网时明确提示"网络不可达"而非"Agent 失败"；本地已完成的 run/step 已落库不丢（R2） |

## 附录 A · 术语

- **群（Group / 圆桌）**：**一个人 + N 个 Agent** 的并行执行单位。借用 IM 界面隐喻，但**不存在第二个人类**（见 §0.1）。
- **群主**：本产品中**等同于"用户"本人**——因为人只有一个。文档中保留该词仅为描述"用户在群视图下的操作视角"，**不隐含权限层级、不隐含存在其他成员**。若某需求的成立依赖"群主 ≠ 其他人"，该需求即属 §0.2 驳回范围。
- **席位（Seat）**：Worker 的执行者身份；本产品中是**上下文隔离单元**，非真实组织角色。
- **扇出（post）**：用户/系统将消息并发投递给多个 Worker。
- **竞速（broadcast）**：全员并行作答，CAS 决出首个有效回复，落选存 `roundtable_alternatives`。
- **HITL**：Human-In-The-Loop，人在回路审批。单机下"回路中的人"恒为本机使用者，无需寻址。
- **MCP**：Model Context Protocol，工具/资源/提示的开放标准。
- **单机（Local-first, single-user）**：无服务端、无账号、状态在本机 SQLite。**不等于离线**——LLM API 与远程 MCP 仍需联网（见 §0.3）。
