结论一（已修订）：方向正确，但赛道已不空。初版判断"组织隐喻派几乎无人做"需要下修——2026 年 6 月起两个重量级开源同类密集入场：阿里 AgentTeams（原 HiClaw，Apache-2.0，K8s 原生 CRD + Matrix 群聊 + Manager/Team/Worker/Human 四类声明式资源）和香港大学 HKUDS AgentSpace（Apache-2.0，数字员工 + AgentRouter 多 harness 归一化 + 审批/预算/看板）。两者都在做"让 Agent 像组织一样运转"，且都比 OneDesktop 走得更远。OneDesktop 剩余的独占位收窄为一条——单机原生桌面、零基础设施、单人开箱即用。

结论二：短板不在架构，在交互层。现有架构方案已覆盖引擎正确性、权限、A2A、执行器多态；但运行期的可见性与可干预性几乎空白——没有 trace 回放、没有成本可见、没有 Worker 侧审批 UI、没有产出物 diff、没有全局待办收敛。这恰是 Claude Code Agent Teams / Devin / CrewAI Traces / LangGraph Studio 建立体验壁垒的地方。

结论三：三条最高杠杆的改动。① Worker 侧 HITL 冒泡到群主会话（当前 Ask 退化为 Deny，工具能力被阉割）；② MCP 从"探活"打通到 tools/call（生态入口，投入产出比最高）；③ 席位卡片 + 运行摘要条上并列"耗时 / token / 预估成本 / 历史成功率"。这三条在补入两个新对手后依然成立，且更紧迫——AgentTeams 与 AgentSpace 均已内建其中全部三项。

结论四（新增）：不要跟进它们的重基础设施，要放大单机的不可复制性。AgentTeams 起步需 Docker + Matrix homeserver + MinIO + Higress 网关（最低 2C4G），AgentSpace 需 Node 24 + PostgreSQL 16 + Google 登录——两者本质是服务端多租户治理平台，面向企业 IT。OneDesktop 若跟着做 RBAC / 多租户 / 网关，会在自己最弱的战场上迎战；正确的做法是把"零部署、本地文件系统直连、离线可用、系统级常驻"做到它们结构上做不到的程度，同时把它们已验证的产品语义（通信拓扑策略、审批深度、诊断视图、记忆分层）低成本移植过来。

01市场格局与 OneDesktop 坐标

把 2026 年的多 Agent 工具摊开看，"如何设计一个 Agent 团队"这件事已经分化成三条互不相同的路线，各自的表达力上限和适用人群差异极大。

路线代表产品设计载体与编排范式上限与代价
画布派 Dify、Coze、Flowise AgentFlow V2、Langflow、n8n、OpenAI Agent Builder 节点图拖拽连线；多 Agent = 多个 Agent 节点 + 条件分支 / 跳转条件 / Tool Mode 端口 上手快、流程可视；但复杂 Agent 的循环、递归、动态成员难以表达。OpenAI 已宣布 Agent Builder 于 2026-11-30 关停
配置代码派 CrewAI（JSONC/YAML）、AG2、LangGraph、OpenAI Agents SDK 代码或声明式配置定义 agent 与拓扑；范式为 sequential / hierarchical / group chat pattern / handoff / state machine 表达力最强、可版本化；但非工程用户无法参与，调试依赖专门工具
组织隐喻派 CrewAI（role/goal/backstory）、Relevance AI（AI Workforce）、Claude Code Agent Teams、Copilot Studio（child/connected agent）、阿里 AgentTeams、港大 AgentSpace、OneDesktop 用"角色 / 席位 / 汇报线 / 群聊 / 派活"组织成员，调度隐含在角色关系中 心智负担最低、非技术用户友好；但运行期可观测性最难做——这是所有该派产品的共同软肋。2026 年 6 月起该派人口密度骤增
站位判断（2026-08-03 修订）：空位被填了一半

初版写的是"桌面端 + 本地文件系统 + 组织隐喻的多 Agent 是一个真实存在的空位"。补入两个新对手后，这句话只有"桌面端"三个字还站得住：

  • 组织隐喻——AgentTeams 把 Manager / Team / Worker / Human 做成了 K8s CRD，连人类都有 L1/L2/L3 权限层级和 accessibleTeams 字段；AgentSpace 把 Agent 定义为"数字员工"，有 owner、readiness、技能绑定，甚至有跨部门借调申请（borrow / transfer request）流程。两者的组织建模都比 OneDesktop 的 SeatType 更完整。
  • 群聊 + 派活——AgentTeams 的 TeamAdmin → TeamLeader → Workers 链路加 Matrix Room，与 OneDesktop 的圆桌几乎同构，且已接入钉钉 / 企微 / 飞书。
  • 本地文件系统——AgentSpace 的 remote daemon 直接在目标主机上跑 Claude Code / Codex，本地文件能力等价；AgentTeams 用 MinIO 做共享文件系统，明确目的是"降低多智能体 token 消耗"。

真正剩下的差异是形态与门槛：AgentTeams 最小依赖是 Docker + Tuwunel(Matrix) + MinIO + Higress 网关，生产形态是 K8s + Helm；AgentSpace 需要 Node.js 24 + PostgreSQL 16 + Google 登录 + 可选远程 daemon。两者都假设"存在一个团队和一套基础设施"。OneDesktop 假设"存在一个人和一台电脑"——这个假设差异才是真正的护城河，也应该是后续所有取舍的第一判据。

三个跨产品的收敛趋势

  • 转移目标（handoff）成为通用语言。AG2 的 Transition Target 枚举、OpenAI 的 transfer_to_<agent> 工具、Coze 的自然语言"跳转条件"、Copilot Studio 把 connected agent 当带描述的工具——本质都是"把可转移目标做成带描述的选项交给 LLM 挑"。OneDesktop 的"群主 @ 派活"是同一机制的人工版，缺的是让 Worker 之间也能直接转移。
  • 共享状态正在从自由字典走向受约束 schema。Flowise 要求在 Start 节点预声明所有 Flow State key（其他节点只能改不能新建）；LangGraph 用 state schema 自动生成输入表单；AG2 的 ContextVariables 支持 ${retry_count} > 3 表达式条件。OneDesktop 的 build_worker_seed 目前是"灌历史"，尚无结构化黑板。
  • 成本已是一等公民。CrewAI Traces 头条显示 total/prompt/completion tokens + 预估成本 + 执行时长；Relevance AI 的 Workforce 看板把"平均每任务成本"和"模型 / eval 通过率"同排展示，让降本与降质同屏权衡。OneDesktop 的 metrics 目前只是内存原子计数，重启即丢。

02OneDesktop 现状盘点（代码级）

以下为走查 src-tauri/src/（71 个 Rust 文件）与 src/（36 个前端文件）后的事实性盘点，作为差距分析的基线。

维度已实现边界 / 缺口
群协作 圆桌双模式（group/roundtable.rs）：post() 按 mentions 扇出并发跑多个 Worker 全部回贴；broadcast() 全员竞速，AtomicBool CAS 决出首个有效回复、取消其余，落选方案存 roundtable_alternatives。Worker 上下文隔离用固定 session rt:<group>:<worker>，RT_TURN_LOCKS 每 Worker 串行防交错，历史上限 40 条溢出压缩。 Worker 之间不能互相转移任务（只有群主能派）；无结构化共享黑板；summarize() 只有一次性汇总，无增量。
席位与派活 SeatType(Static/Dynamic/Capability) + WorkerPool pick/acquire/release；TaskScheduler 批次派活，depends_on 构成 DAG，依赖全 Completed 才释放；dispatch_lock 原子认领防重复。 DAG 仅表单录入（复选框选依赖），无可视化拓扑、无看板拖拽；无任务超时 / 心跳，Worker 卡死则依赖链永久阻塞。
Agent 定义 AgentProfile（group/agent_profile.rs + agents 表）含 name / model / system_prompt / capabilities / skills / mcp / tools / token_budget / provider；capabilities_block() 把能力注入 system prompt 的 [Capabilities] 段。 无模板、无市场、无导入导出，复用仅限库内 CRUD；无法从 .claude/agents 等既有生态导入。
工具与扩展 内置仅三类：filesystem（Read/Write/ListDir，已有 resolve_fs_path workspace 强制隔离）、shell（RunShell）、memory（UpdateMemory）。Skill 支持 local/url/builtin 三源，解析 SKILL.md frontmatter。 MCP 只做了连通性探活（mcp/client.rs 的 initialize + list 三件套），全仓无 tools/call 调用路径——外部工具生态实际未打通。Plugin 仅 UI 占位。定时任务的 skill action 明确未接通。
HITL 三态权限（agent/permission.rs）：Allow/Deny/Ask × SessionKind(User/Worker) fail-closed 矩阵，覆盖存 tool_permissions 表。用户会话 Ask 会弹审批。 Worker 侧无审批 UI，Ask 退化为 Deny；群内 Worker 的 run_shell / update_memory 默认直接 Deny，工具能力被阉割。无 edit-args、无超时兜底、无审批审计。
可观测性 telemetry/metrics.rs 的 Metrics 原子计数（agent_loops / tool_calls / total_tokens）；前端 ProcessPanel.tsx 渲染工具步骤 + 审批按钮 + shell 输出 <pre>。 不持久化、重启即丢、无 per-conversation 成本；无 trace 树、无步骤时间线、无回放、无失败下钻。
前端形态 App.tsx 导航 NavKey(chat/tasks) × ChatMode(session/group)；GroupsPage.tsx（2327 行）三视图：GroupRoundtable（消息 + @ 选择器 + 摘要）/ GroupDispatch（任务草稿表单）/ GroupDeliverables（产出物抽屉），订阅实时刷新。 无可视化编排画布；无 diff / 文件预览 / 交互终端；产出物只能看不能比对；无跨群的全局待办视图。
数据模型 SQLite（WAL + Mutex<Connection>）16 张表：sessions / messages / session_summaries / agents / groups / workers / tasks / roundtable_* ×3 / scheduled_tasks / mcp_servers / skills / worker_metrics / tool_permissions / settings。 单连接全局串行（已在架构方案 P1-8 列为资源治理项）；无 trace / run 表，无成本记账表。

A 组 · 编排设计工具

LangGraph Studio / Agent Inbox 调试交互标杆

LangChain · 代码定义 + 可视化只读渲染

不做双向同步的画布，而是代码定义图、Studio 渲染并提供强交互调试——这个折中避免了画布与代码同步的地狱。

  • 节点级断点：Interrupt 按钮可选任一节点并指定 before/after
  • Edit state → Fork 与 Re-run from here 拆成两个明确动作（改状态分叉 vs 换配置重跑）
  • 信息密度滑杆：一根滑杆控制 trace 展开层级（turn → node → state key）

  • Agent Inbox：Gmail 式收件箱收敛所有待审批，条目可"Open in Studio"跳回现场
Claude Code · Subagents + Agent Teams 最接近 OneDesktop

Anthropic · Markdown frontmatter 定义 + 终端 UI

与 OneDesktop 的席位模型几乎同构，成熟度更高，是最直接的对标对象。

  • Agent 定义 .claude/agents/*.md：仅 name/description 必填，可选 tools/disallowedTools/model(inherit)/permissionMode 七态/maxTurns/skills/mcpServers/hooks/memory/isolation: worktree/color
  • Teams 四组件：Lead / Teammates（各自完整会话）/ 共享任务列表（三态 + 依赖自动解锁 + 文件锁防重复认领） / Mailbox（SendMessage 点对点 + broadcast）
  • 权限冒泡：Teammate 的审批统一冒到 Lead 会话；Teammate 不能代用户批准；被拒操作不能转交他人绕过；Plan 审批由 Lead 直接批不打扰用户
  • UI：单栏 in-process（Shift+↓ 轮播 teammate，Enter 进入，Esc 打断，Ctrl+T 叠加共享任务列表）+ 可选分屏
  • Skills 三级预算：L1 元数据常驻约 100 token / L2 正文 <5k / L3 捆绑文件按需（未读 = 0 token）
  • Hooks 30+ 事件，PreToolUse 可返回 allow|deny|ask|defer 并用 updatedInput 改写参数后放行
CrewAI / CrewAI AMP 组织隐喻 + 成本可视

JSONC/YAML 配置 · Visual Agent Builder

  • Agent 三件套必填 role / goal / backstory；可选 max_iter(20) / max_rpm / max_execution_time / allow_delegation / reasoning / respect_context_window（超窗自动摘要）/ knowledge_sources / step_callback
  • 两种 Process：sequential（前步输出成为后步 context）与 hierarchical（必须配 manager_llm，任务不预分配、manager 规划委派校验）
  • Traces 页可直接移植：头条固定 total/prompt/completion tokens、请求数、耗时、预估成本；下方任务级甘特时间线，可按任务下钻看 Agent / LLM / 输入 / 输出 / 状态
AutoGen Studio / AG2

Microsoft · 拖拽 + 声明式 JSON 双向编辑

  • 四界面：Team Builder / Playground / Gallery（社区组件导入）/ Deployment（导出 Python、Docker）
  • Playground 用 control transition graph 可视化"发言权转移"，运行中可 pause/stop
  • AG2 五种 Pattern：Auto（LLM 选下一发言者）/ RoundRobin / Random / Manual（人工选下一个发言者） / Default

Coze（扣子）

字节 · 多 Agent 作为一等模式开关

  • Single ↔ Multiple agents mode 一键切换，页面变四区（编排面板 / Agent 画布 / 预览调试）
  • 节点内 Jump Condition 用自然语言描述适用场景，由前序节点判断切换；另有全局跳转节点（上限 5，优先级更高）
  • 每个 Agent 独立模型 / 提示词 / 插件 / 知识库 / 工作流，支持"创建副本"
  • 回复气泡上带绿色标签标明"由哪个 Agent 回答"，可单独调试某个节点
Flowise AgentFlow V2 / Langflow / n8n

开源画布三件套

  • Flowise Flow State：必须在 Start 节点预声明所有 key 与默认值，其他节点只能更新不能新建——给多 Agent 黑板加 schema 约束
  • Flowise Human Input 节点有 proceed / reject 两个输出锚点，把人类决策变成显式分支；工具可单独设"执行前需人工许可"
  • Langflow Tool Mode：任意组件（含另一个 Agent、MCP Server）打开后长出 Toolset 端口，拖一根线即完成 agent-as-tool
  • n8n Wait 节点：内置表单构建器（Text/Number/Date/Dropdown + 必填）+ Limit Wait Time 超时自动继续——审批超时兜底的现成范式

B 组 · 协作型 Agent 产品

Devin（Cognition） 长任务可见性标杆

云端 · 组织知识资产化

  • Work Log 折叠手风琴：每步带 🟢/🟠/🔴 自评等级 + 时间戳 + 耗时，能直接跳到出问题的那一步——长任务信息密度最高的呈现方式
  • Global Work Diff：任意时间点的全部改动汇总 + 单文件编辑历史 + 跨所有 shell 的 Command History
  • Playbooks：可复用的步骤 + 成功标准 + 护栏文档，组织内共享，有"Past runs"看同事怎么用，发送前可 inline 编辑并选择"更新库中版本"或"另存为新 Playbook"
  • Knowledge：按 trigger 条件注入的组织常识（如 trigger="改 API 路由" → "我们用 Fastify 不是 Express"）
  • Machine Snapshots（环境存档 + 启动命令序列）、Devin Wiki（自动索引仓库生成带架构图的文档）
Manus 含重要反面教训

云 VM 沙箱 · 任务回放

  • 每 session 一台专属 VM，典型任务约 50 次工具调用；三层动作空间：<20 个原子 function → sandbox CLI 工具 → Python 脚本调预授权 API
  • 工具结果有 full / compact 两种表示：full 存沙箱，compact 只留文件路径引用；对陈旧结果做 compaction，收益递减后再做 summarization
  • 检索靠 glob/grep，不用向量库
  • 教训：todo.md 最初用于对抗 lost-in-the-middle，后来发现约 1/3 的动作都花在更新 todo 上，改为 planner agent + executor 子 agent + knowledge manager。子 agent 的目的被明确定义为隔离上下文，而非模仿人类分工
Cursor 2.0

并行隔离 + 评审瓶颈

  • 界面围绕 agent 而非文件重构（可切回经典 IDE）；并行 agent 用 git worktree 或远程机器隔离
  • 官方把"代码评审"和"变更测试"列为 agent 时代的两个新瓶颈，因此内置 browser tool 让 agent 自测，并简化"快速审阅全部改动"的 UI
  • diff 随 agent 工作实时渲染，方向错了可随时 Stop 改道，不必等跑完；@Branch 给 agent 当前分支完整 diff；Source Control 可跑 Agent Review 对 main 整体审查

注：三方博客流传的"8 个并行 agent""best-of-n 提升 20%"未在官方文档确认。

Relevance AI 运营看板可直接抄

AI Workforce 组织隐喻

  • Agent 职位化命名（Lead Researcher / Inbound Qualifier / Deal Reviewer）+ 头像 + 绑定 app 图标
  • 三种构建路径共用同一 runtime 与同一套 eval 门禁：拖拽画布（agents + tools + approvals 节点）、Build with AI、Build with MCP（工程师从 Claude Code / Cursor 里经 MCP 建 agent）
  • Workforce 看板：每 agent 一行，列出 Task / 工具图标 / 所用模型 / Eval 通过率 / 平均每任务成本；顶部汇总 Tasks run/mo、Spend/mo、Avg cost/task；按 2% 采样 live runs 画通过率曲线侦测 drift
Lindy AI

Societies of Lindies

  • 多 Agent 机制朴素但可抄：接收方挂 Agent Message Received 触发器，发送方加 Agent Send Message 动作，下拉只列有触发器的 agent，并可选择传递哪部分上下文（明确以降 token 为目的）
  • 任务面板运维交互完整：可搜索、按"报错/未读"过滤、单动作一键 retry、右键 terminate（同时阻断后续联动）、任意任务生成公开分享链接
  • Loop 步骤支持 Max Cycles + Max Concurrent；提供 Task Completed 触发器与 Get Task List/Disable Agent 让 agent 监控 agent
OpenHands / Copilot Studio / Zapier Agents

补充观察

  • OpenHands：技能合并优先级 public < user < organization < project < sandbox（同名后者覆盖）；启动是显式状态机——WAITING_FOR_SANDBOX → PREPARING_REPOSITORY → RUNNING_SETUP_SCRIPT → SETTING_UP_SKILLS → READY，冷启动体验很值得桌面端参考
  • Copilot Studio：给出经验阈值——主 agent 可选动作（工具 + topic + agent）超过 30–40 个时表现退化，这是拆分子 agent 的信号；痛点是每个 connected agent 生成独立 transcript，需靠 telemetry ID 关联父子会话
  • Zapier Agents：反面案例——审批历史只存在会话中、不持久化为审计轨迹（三方实测）；正面是 AI Guardrails 内置输入侧 PII / prompt injection 筛查

阿里 AgentTeams（原 HiClaw） 组织建模最彻底

  • 把组织结构做成了 K8s CRD。apiVersion: hiclaw.io/v1beta1 下四种 Kind：Manager（平台管控，建 Team / 建 Human / 配权限，不进 Team Room、不 @ Worker）、Team（一个 TeamAdmin + 一个 TeamLeader + N 个 Worker）、Worker（最小执行单元 = 容器 + Matrix 账号 + MinIO 空间 + Gateway Consumer）、Human（真人 + L1/L2/L3 权限 + accessibleTeams/accessibleWorkers）。业务协作链路是 TeamAdmin（真人）→ TeamLeader（协调型 Worker）→ Workers，"老板不越级管理"被做成房间拓扑约束。
  • "谁能跟谁说话"是策略不是约定。Worker 之间能否互 @ 由 Team 的 peerMentions 字段控制，能否跨 Team @ 由各自的 channelPolicy 控制。OneDesktop 完全没有这一层
  • Worker 携带四份声明式文件：SOUL.md / AGENT.md / MEMORY.md / USER.md，能力边界写在 AGENT.md 里由 hiclaw-controller 运行时 reconcile。
  • Matrix 作为通信底座（Tuwunel homeserver + Element Web），并桥接钉钉 / 企微 / 飞书。协议级解耦带来一个关键能力：一个 Team 内可混编异构运行时——OpenClaw(Node) / QwenPaw(Python，原 CoPaw) / Hermes（带终端沙箱与持久记忆），Manager 也可选运行时。
  • 凭证零信任：Higress AI Gateway 持有真实凭证，每个 Worker 只拿可吊销的 Consumer Token，网关做 per-route allowedConsumers 授权；派生凭证自带 Tenant / Team / Worker 三级标签，MCP 凭证按需下发、用后销毁、不可转发不可持久化。
  • 三层记忆（ReMe）：L1 短期写 session/dialog/，auto_memory hook 每次回复后把事实卡片 / 摘要写入 daily/；L2 长期整理为 digest/{personal, procedure, wiki}/；L3 auto_dream 定时任务对当日 daily 做蒸馏 / 纠错 / 去重 / 合并并输出"醒来报告"。Worker 退役时 cleanup hook 整体归档或销毁其 workspace 目录，防止残留泄漏。
  • 可观测性基于 OpenTelemetry Trace，token 成本按 Team / Agent / Model 三个维度拆账。共享文件系统（MinIO/OSS）的官方定位是"降低多智能体 token 消耗"。
  • 部署：本地 curl | bash 一键起（Docker，2C4G 起）或 K8s + Helm；商业版跑在独立云账号 / VPC / 安全沙箱。阿里内部已用它跑 15 个 Agent、4 个闭环场景（研发全链路 / 7×24 值班答疑 / 开源流水线 / 经营驾驶舱）。
港大 AgentSpace（HKUDS） 运行时归一化 + 治理面最完整

Apache-2.0 · github.com/HKUDS/AgentSpace · 首提交 2026-06-22，约一个月 142 commits · Next.js + PostgreSQL

  • 核心创新是 AgentRouter——"provider harness normalization layer"。原文定位："It does not replace the workspace or own the business queue. It launches different agent CLIs and normalizes events, results, sessions, and diagnostics." 关键点是Agent 的身份、指令、技能、知识、权限保持不变，只有执行 harness 变化。与 OneDesktop P2-13 的 CliExecutor/CliAdapter 是同一思路，强力验证了该方向
  • 已支持 8 种运行时，且每种都有独立诊断策略：Claude Code（stream-json 事件 + session fallback + tool approval bridge）、Codex CLI（JSON 事件 + 运行时工具能力诊断）、Antigravity CLI（agy -p prompt 模式 + 会话复用 + timeout/nonzero/empty 诊断）、OpenCode（session 传播）、OpenClaw（health / preflight + auth/profile/model/tool/protocol 五类诊断）、Hermes（可执行文件兼容性检查）、Gemini CLI 与 NanoBot 走 legacy one-shot 回退。

  • 诊断即一等公民：权限控制面里专门有 Diagnostics 维度，列出 missing grants / revoked credentials / orphaned grants / unavailable providers。这是个很聪明的产品设计——把"为什么这个 Agent 干不了活"变成可枚举清单
  • 审批做成了快循环：原文 "High-impact actions route directly into human approvals, with a fast TabTabTab-style approval loop"；风险动作在发生之前被标记——tool use / document access / external sends / budget-sensitive actions。
  • 数字员工可签名导出：agent-space employee export-persona --name <employee> --sign 导出为 signed OpenAgent persona-card；operator instructions、skills、owner identity 默认脱敏，需显式 --include-sensitive 才嵌入。
  • 另有：知识库 + 全局搜索、任务看板、预算 / 成本 / 绩效仪表盘、附件与可靠通知、远程 daemon 与 runtime 共享。
  • Roadmap（尚未实现）：更强的 AgentRouter 平台会话、多 Agent 隔离与沙箱策略层、完整集成适配器契约、运行时工具市场、更严格的附件签名 URL 与存储隔离。

从 AgentTeams 偷到的最有价值的一条：不是技术，是判断标准

阿里在博客里明确写了"并非所有 Agent 场景都需要群聊"："If it's just writing a piece of code, looking up a document, or generating an image, a single chat is a more direct and lower-cost option. The cost of introducing group chats is non-trivial." 并给出三条正向判据——① 跨域协作与长时工作流；② 多 Agent 治理（需要清晰的信任边界、归属、授权、计费）；③ 组织级知识沉淀。同时给出了群聊的本质定义："group chat ≠ the sum of multiple individuals chatting with a bot separately"——如果每个人都有自己的 session，那只是并行的单聊。

对 OneDesktop 的直接启示：群协作是重型工具，不该是默认入口。当前产品里"建群"的心智成本明显高于"发一句话"，但两者之间没有平滑升级路径。应该做的是：普通会话里当任务复杂到需要多 Agent 时，提供"把这个会话升级为群"的一键操作，把已有上下文作为群的初始共享状态带过去——而不是让用户先想清楚要几个席位再开始。

MCP 版本时效提醒（重要）

截至 2026-08-03，MCP 当前规范版本是 2026-07-28（刚发布），含破坏性变更：删除 initialize 握手与 Mcp-Session-Id，协议无状态化；新增强制 server/discover；所有 result 必须带 resultType（complete / input_required）。更要命的是——sampling / roots / logging 在该版本已标记 Deprecated（SEP-2577），官方建议 sampling 改为直接对接 LLM Provider API。建议 OneDesktop 按 2025-06-18 打底、2025-11-25 增强落地（SDK 生态成熟），但不要新建 sampling/roots 实现，并把"会话"抽象成可丢弃对象为无状态化预留。

标准对 OneDesktop 的可执行结论
MCP tools/call入参 {name, arguments}；工具名 1–128 字符仅 A-Za-z0-9_-.，多服务器聚合时客户端自己加前缀消歧（server name 不保证唯一）。必须区分两类错误：协议错误走 JSON-RPC error（未知工具 -32602），工具执行错误走 result.isError=true 并把内容喂回模型让它自愈。客户端 SHOULD 为每次调用实现超时；实现 notifications/progress 与 notifications/cancelled；建议现在就做 list 缓存层（2026 版改为显式 subscriptions/listen + ttlMs）。
tool annotationsreadOnlyHint(默认 false) / destructiveHint(默认 true) / idempotentHint / openWorldHint。规范原文强调"除非来自受信服务器，客户端 MUST 视 annotations 为不可信"——只能用于降级默认策略的建议值（如 readOnlyHint=true 默认 Allow），绝不能自动提权；未声明即按危险处理。这与 OneDesktop 的三态权限矩阵天然契合。
MCP elicitation保留且值得做。form 模式（扁平对象、基础类型 + minLength/format/default）与 url 模式（敏感凭证必须走 URL，客户端不得预取、必须展示完整域名）。响应三态 accept / decline / cancel，与 Allow/Deny/Ask 是正交两层，不要混用。
OAuthMCP Server = OAuth 2.1 Resource Server，MUST 实现 RFC 9728 Protected Resource Metadata；客户端 MUST 实现 RFC 8707 resource 参数与 RFC 9207 iss 校验。DCR 已弃用，优先 Client ID Metadata Documents（client_id 就是指向自管 JSON 的 URL）——对桌面应用极友好。stdio 传输 SHOULD NOT 走 OAuth，从环境变量取凭证。
A2A v1.0已在现有架构方案 P2-14 覆盖。补充两点：v1.0 用 supportedInterfaces（有序列表，首项优先）取代了 v0.x 的 url/preferredTransport，且新增 Signed Agent Card（JWS）；Message 用于交互、Artifact 才是任务输出，OneDesktop 的 deliverables 应映射到 Artifact 而非 Message。
AGENTS.mdOpenAI 2025-08 发布，60,000+ 仓库采用，2025-12 捐入 Agentic AI Foundation。纯 Markdown 无强制 schema，monorepo 用嵌套文件就近优先。成本极低、收益确定：OneDesktop 应把 AGENTS.md 作为项目级上下文的读取入口。
Agent 定义格式不存在可移植标准，各家碎片化（Claude Code .claude/agents/*.md、Cursor、Codex TOML、Kiro JSON…）。建议：内部定义规范化 Agent Manifest，再写双向适配器导入/导出 .claude/agents；对外互操作用 A2A AgentCard（目前唯一有标准地位的描述格式，但只描述对外服务契约、不含 system prompt）。
HITL schemaLangGraph HumanInterrupt{action_request, config{allow_accept/edit/respond/ignore}, description} + HumanResponse{type, args} 是事实标准。约定：四项全 false 时 UI 默认允许 ignore，防止线程卡死。注意 LangGraph 的最大坑——恢复时整个节点从头重放，interrupt 之前的副作用必须幂等。

从矩阵读出的五个洞察

  1. OneDesktop 强在"编排语义"，弱在"运行期"。组织隐喻 + 三种派发语义（扇出 / 竞速 / DAG）在整张表里名列前茅——竞速择优这一项，连两个新对手也都没有（AgentTeams 是 Leader 单点分派，AgentSpace 是队列路由，均无并行择优）。但从"运行期 trace"往下的五行几乎全是空白。产品的说服力发生在运行期，而不是配置期。
  2. MCP 依然是唯一的"生态断点"，且现在更刺眼。这是全表唯一一个"人人都有、只有 OneDesktop 没有"的能力，两个新对手也不例外——AgentTeams 做到了声明式 MCP + 网关托管 + REST 零代码转 MCP，AgentSpace 直接继承 harness 的工具生态。它不是加分项而是入场券。
  3. Agent 定义不可移植是复用性天花板，且对手已经走到了"签名导出"。竞品普遍有模板库 / Gallery / Playbook / 组织级共享；AgentTeams 的 TeamSpec 把"角色配置 + 技能组合 + 协作策略"打包成可复用团队蓝图，AgentSpace 能把数字员工导出为签名的 persona-card 且敏感字段默认脱敏。OneDesktop 的 AgentProfile 还只能库内 CRUD。桌面端的杀手锏依然是"从 .claude/agents 一键导入"——这是云端与服务端产品都做不到的本地生态红利。
  4. 补入两列后，OneDesktop 的"绝对领先项"归零，"绝对独占项"只剩一个。原本靠"组织隐喻 + 本地文件系统"支撑的差异化，被 AgentTeams（组织建模更深）和 AgentSpace（本地 daemon + 8 种 harness）分别覆盖。唯一保住满分独占的是最后一行——零基础设施、单人开箱即用。这不是安慰奖：它意味着 OneDesktop 面向的是"一个人想指挥一队 Agent"，而不是"一个公司想治理一群 Agent"，这两件事的产品形态、默认值和交互密度都应该不同。
  5. 产出物 diff 是全表公认的空白（仅 Devin 一家满分）。包括两个新对手在内，10 个产品里 8 个是 ○。当 Agent 真的动了本地文件，"它到底改了什么"是用户唯一真正关心的问题。桌面端天然握着本地文件与 git，做变更集审阅的成本远低于任何云端或容器化产品——这是被整个市场忽略、而 OneDesktop 有结构性优势的一格。

每项标注优先级与"和现有 architecture-adjustment-plan.md 的关系"。计划内 表示方案已覆盖、此处只补充细节；需扩展 表示方案有骨架但缺产品层；新增 表示方案未涉及。

P0新增F1 · MCP 从"探活"打通到 tools/call
现状
mcp/client.rs 只做 initialize → tools/list → resources/list → prompts/list 握手验证连通性，全仓无 tools/call 路径。已配置的 MCP Server 在 Agent 循环里实际不可用。
影响
这是能力矩阵里唯一"人人都有、只有我们没有"的项。Agent 被锁死在 filesystem / shell / memory 三个内置工具上，席位再多也无米下锅。投入产出比全表最高。
做法
把 MCP 工具注册进 ToolRegistry，实现 ExecutableTool 的 MCP 适配器。四个必须做对的点：① 多服务器聚合时客户端自己加前缀消歧（mcp__<server>__<tool>，同时兼容 Claude Code 的授权模式匹配语法）；② 区分协议错误与工具执行错误——后者走 isError=true 把内容喂回模型自愈，不要当异常抛；③ 每次调用实现超时 + notifications/cancelled（可复用 P0-4 已落地的异步工具取消机制）；④ 加 tools list 缓存层，为 2026-07-28 的 subscriptions/listen + ttlMs 预留。
落点
src-tauri/src/mcp/client.rs、agent/tool_registry.rs、agent/tools/mod.rs
P0需扩展F2 · Worker 侧 HITL 冒泡与四态响应
现状
三态权限矩阵已有，但 Worker 会话的 Ask 因为没有审批 UI 而退化为 Deny；群协作路径为了避免挂死统一传 auto_approve_override: Some(true)（2026-08-02 的挂死修复）。等于在"全放行"和"全拒绝"之间二选一。
参考
Claude Code Agent Teams 的权限设计几乎是为这个问题量身定做：Teammate 的权限提示统一冒泡到 Lead 会话中审批；Teammate 不能代替用户批准；被拒的操作不能转交别的 Teammate 绕过；auto 模式下把"另一个 agent 转述的批准"视为不可信输入。Plan 类审批则由 Lead 直接批、不打扰用户。
做法
① 把 Worker 的 Ask 请求冒泡到群主会话，UI 上标明"Worker X 请求执行 Y"；② 审批契约升级为 LangGraph Agent Inbox 的 schema——config{allow_accept, allow_edit, allow_respond, allow_ignore} 决定渲染哪几个按钮，响应 accept / edit / respond / ignore，其中 edit（改参数后放行）是当前完全缺失但价值最高的一态；③ 四项全 false 时默认允许 ignore 防卡死；④ 按 tool annotation 分级设 TTL（readOnlyHint 长、destructiveHint 短），超时默认 Deny（fail-closed）并把超时作为 ignore 写入审计。
落点
agent/permission.rs、agent/engine.rs（auto_approve_override 处）、group/roundtable.rs、前端 ProcessPanel.tsx + 新的审批组件
P0需扩展F3 · 运行记账：trace 与成本持久化
现状
telemetry/metrics.rs 只有内存 AtomicU64 计数，重启即丢；无 per-conversation / per-worker / per-task 的 token 与成本。架构方案 P2-11 列了"可观测性"但定位为独立小项。
建议
升级为 P0 并前移——理由：F2 的审批审计、后面所有交互改进（运行摘要条、席位成本、事前预估）都依赖这份数据，它是底座而非叶子。
做法
新增 runs / run_steps 两张表：run 记录 group / task / worker / 起止时间 / stop_reason（P0-1 已有 AgentRunOutcome，直接落库）/ prompt&completion tokens / 预估成本；step 记录工具名 / 入参摘要 / 耗时 / 成功失败 / 审批决策。成本用 provider × model 的单价表本地换算。
落点
telemetry/metrics.rs、storage/connection.rs、agent/engine.rs（复用 P0-1 的 AgentRunOutcome）
P1新增F4 · Agent 定义可移植：Manifest + 双向适配器 + 模板库
现状
AgentProfile 只能库内 CRUD，无模板、无导入导出。
参考
行业不存在可移植的 Agent 描述格式（Claude Code md / Cursor / Codex toml / Kiro json 各自为政），但 Claude Code 的 .claude/agents/*.md 事实上覆盖面最广，且字段与 AgentProfile 高度同构：name / description / tools / disallowedTools / model(inherit) / permissionMode / maxTurns / skills / mcpServers / 正文即 system prompt。

落点
group/agent_profile.rs、skill/manager.rs（已有 frontmatter 解析能力可复用）、extensibility/ExtensibilityPage.tsx
P1新增F5 · Worker 间直接通信与转移
现状
只有"群主 @ 派活"这一条边，Worker 之间无法直接对话或转移任务。星形拓扑，群主是唯一枢纽。
参考
Claude Code 的 Mailbox（SendMessage 点对点 + broadcast，消息自动投递无需轮询，空闲/报错自动通知 Lead）；Lindy 的 Agent Message Received 触发器 + 可选择传递哪部分上下文（明确以降 token 为目的）；AG2 的 Transition Target 枚举。

agent/tools/ 新增工具、group/roundtable.rs（复用现有 RoundtableBus）
P1新增F6 · 任务心跳与依赖链防死锁
现状
DAG 依赖靠"前置全 Completed 才释放"，但无超时、无心跳。Worker 卡死或漏标完成 → 后继任务永久阻塞。
参考
Claude Code Agent Teams 官方已知限制里明确列了这一条："任务状态可能滞后导致依赖卡死"——说明这是该模式的固有陷阱，不是实现瑕疵。n8n 的 Limit Wait Time 给出了兜底范式。
做法
任务加 heartbeat_at 与 deadline；调度器 tick 时检测超时任务 → 标 Failed 并通知群主 → 提供"重试 / 改派他人 / 跳过依赖"三个动作。TeammateIdle 式的空闲检测也归入此处。
落点
group/scheduler.rs、group/task_board.rs、scheduler/engine.rs（1 秒 ticker 可复用）
P1需扩展F7 · 结构化共享黑板
现状
build_worker_seed（2026-08-03 落地）把群共享日志灌给 Worker，解决了"完全失忆"；P0-2 又加了任务卡注入。但共享状态仍是自由文本，没有结构。
参考
Flowise 的 Flow State：Start 节点预声明所有 key 与默认值，其他节点只能更新不能新建；AG2 的 ContextVariables 支持 ${retry_count} > 3 表达式条件；LangGraph 用 state schema 自动生成输入表单。
做法
群级增加 shared_state（建群时声明 key + 类型 + 默认值），Worker 通过工具读写但不能新建 key。收益有三：Worker 之间传递结构化结论而非叙述；条件派活可写表达式；前端能把黑板渲染成表格实时展示。这也顺带解决 A2A 映射时 Artifact 的结构化问题。
落点
group/group.rs、group/roundtable.rs（build_worker_seed 处）、新增内置工具
P1需扩展F8 · Skill 三级预算加载 + 调度 skill action 接通
现状
Skill 支持 local/url/builtin 三源并解析 frontmatter，但加载策略未分级；scheduler/engine.rs 的 skill action 明确记录"Skill 执行暂未接通"。
参考
Claude Code 的 progressive disclosure 三级预算：L1 元数据常驻约 100 token / L2 正文 <5k token / L3 捆绑文件按需读取（未访问 = 0 token），脚本"只进输出不进上下文"。约束：description 必须同时写清 what + when。
做法
把 capabilities_block() 的 skill 注入改为只注 L1 元数据，命中后才读正文；捆绑脚本走 shell 执行只回收输出。对多 Worker 场景收益被放大 N 倍——每个 Worker 都有独立上下文，省的 token 是乘法关系。同时补齐 scheduler 的 skill action。
落点
skill/manager.rs、group/agent_profile.rs（capabilities_block）、scheduler/engine.rs
P2新增F9 · 组织知识资产：Playbook + 条件注入 Knowledge
参考
Devin 的双资产设计：Playbook（可复用的步骤 + 成功标准 + 护栏，"像程序但没有严格语法"，有 Past runs 看别人怎么用，发送前可 inline 编辑并选择更新库中版本或另存为新的）；Knowledge（按 trigger 条件注入，如 trigger="改 API 路由" → "我们用 Fastify"）。
为什么值得
OneDesktop 已有 task.reasoning（任务卡拆解依据）和 roundtable_summaries，离"把一次成功的派活固化成 Playbook"只差一步：给成功的群任务加"存为 Playbook"按钮，下次建群时可一键套用成员配置 + 任务 DAG + 拆解依据。这是把一次性执行变成组织资产的最短路径。
顺带
低成本高确定性的一项：把 AGENTS.md 作为项目级上下文的读取入口（60,000+ 仓库已采用，已捐入 Agentic AI Foundation），workspace 内有该文件就自动注入。
P2新增F10 · 并行隔离与变更集
现状
多 Worker 并发写同一 workspace，无隔离。resolve_fs_path 防的是越界，不防互相覆盖。
参考
行业已收敛到 git worktree 隔离 + 延迟到显式合并点：Cursor 2.0 用 worktree/远程机器隔离并行 agent，Claude Code 把 isolation: worktree 做成 frontmatter 字段并配 WorktreeCreate/WorktreeRemove hook。另一条纪律是给每个 worker 分配互不相交的文件集（Claude Code 明确警告同文件并发编辑会互相覆盖）。
做法
分两步：① 短期——派活表单支持声明"文件范围"，调度器检测重叠并警告；② 中期——git 仓库场景走 worktree，非 git 场景自建"变更集 = 文件级快照 + 可回滚"抽象（OneDesktop 面对的文档 / 表格场景 worktree 不适用，这点必须自研）。

P1需扩展F11 · CLI 执行器的可诊断性（对标 AgentRouter）
现状
架构方案 P2-13 已有 CliExecutor / CliAdapter，覆盖 codex / opencode / pi / claude。方向正确，但目前只解决"能把外部 CLI 跑起来"。
参考
AgentSpace 的 AgentRouter 是同一思路的成熟版，且明确划清了边界："It does not replace the workspace or own the business queue. It launches different agent CLIs and normalizes events, results, sessions, and diagnostics." 关键在于它为每个 provider 单独定义了诊断策略：Claude Code 解析 stream-json 事件并做 session fallback、还架了 tool approval bridge；Codex 有 runtime tool capability diagnostics；OpenClaw 有 health / preflight 预检与 auth/profile/model/tool/protocol 五类错误分类；Antigravity / OpenCode / Hermes 各有 timeout / nonzero-exit / empty-response 三态诊断。
做法
给 CliAdapter trait 补三个方法：① preflight() —— 启动前检查可执行文件存在性、版本兼容、认证状态、模型可用性，把失败前置到席位配置时而不是任务执行到一半；② classify_failure() —— 把退出码 / 空输出 / 超时归一化为可枚举原因，而不是抛一坨 stderr；③ session_fallback() —— 会话 ID 丢失时降级为一次性调用而不是整轮失败。另外把 Claude Code 的 tool approval bridge 接进来，让外部 CLI 的权限请求也能走 F2 的冒泡审批，否则外部席位会成为权限体系的黑洞。
落点
agent/executor/cli.rs（P2-13 落点）、agent/permission.rs
P1新增F12 · 通信拓扑策略化："谁能跟谁说话"不该是硬编码
现状
roundtable.rs 的 post() 是全员扇出——每条消息广播给群内所有席位。拓扑固定为星形，唯一变量是群主决定 @ 谁。席位之间的可见性、能否互相触发，都没有表达方式。
参考
AgentTeams 把这件事做成了 CRD 字段：Worker 之间能否互 @ 由 Team 的 peerMentions 控制，能否跨 Team @ 由各自 channelPolicy 控制；Human 侧有 accessibleTeams / accessibleWorkers。产品原话是"一切'谁能跟谁说话'都是策略，不是约定"。它甚至把"老板不越级管理"（TeamAdmin 只在 Leader DM Room 里与 TeamLeader 对话）做成房间拓扑层面的约束。AgentSpace 对应的是频道准入 + 私聊隐私范围。
为什么值得
三重收益，且改动量小：① 省 token——扇出规模是多 Agent 成本的主要来源，Claude Code 官方也警告 broadcast 成本随团队规模成倍增长；② 降噪——席位不必读与自己无关的消息，上下文更干净；③ 是 F5（Worker 间直接通信）的前置——没有拓扑策略就放开互相 @，会立刻退化成消息风暴。建议 F12 先于 F5 落地。
做法
群配置增加 peer_mentions: bool（默认 false）与席位级 visible_to: Vec<SeatId>（默认全体，可收窄）；post() 按策略过滤投递目标。UI 上在建群页给一个"协作拓扑"的三选一预设：星形（默认，群主中枢）/ 全连通 / 自定义，不要一上来就暴露字段。
落点
group/group.rs、group/roundtable.rs（post() / broadcast()）、GroupsPage.tsx 建群弹窗
P2新增F13 · 凭证不落 Worker（单机版零信任）
参考
AgentTeams 的做法值得注意，因为它是被真实企业安全需求逼出来的：Higress AI Gateway 持有全部上游真凭证（LLM API Key、MCP 上游 Token、内部服务账号），每个 Worker 只拿一个可吊销的 Consumer Token，网关做 per-route allowedConsumers 授权；派生凭证自带 Tenant / Team / Worker 三级标签，"blast radius is strictly limited"；MCP 凭证按需下发、用后销毁、不可转发不可持久化。AgentSpace 对应的是 runtime grants + 可吊销 daemon API token + agent-scoped OAuth 委托。
对单机的翻译
不需要网关，但核心原则可以极低成本地照搬：① 凭证只留在 Rust 主进程，不通过环境变量注入外部 CLI 子进程（当前 CliExecutor 很可能是直接透传 env，这是最容易被忽略的泄漏面——子进程的 /proc/<pid>/environ 和崩溃日志都可能带出 key）；② 席位级声明"可访问哪些 MCP Server / 哪些 Provider"，在 ToolRegistry 层做准入而不是靠 prompt 约束；③ 每个凭证的使用记录进 F3 的 run_steps，做到"哪个席位在什么时候用了哪个 key"可查。
落点
agent/executor/cli.rs、mcp/client.rs、agent/tool_registry.rs、storage/
P2新增F14 · 记忆分层、定时蒸馏与席位退役清理
现状
内置 memory 工具是扁平的：一个平面的键值/文本存储，无分层、无衰减、无蒸馏。多 Worker 场景下，每个席位往里写、所有席位一起读，随时间只会越来越脏。Worker 从 WorkerPool 退出时也没有 workspace 清理动作。
参考
AgentTeams 的 ReMe 三层值得整体借鉴：L1 短期——原始对话流写 session/dialog/，auto_memory hook 在每次回复后把事实卡片 / 对话摘要 / 资源阅读笔记写入当日 daily/，"只关心今天发生了什么，结构化可审计，不直接参与在线召回"；L2 长期——整理为 digest/{personal, procedure, wiki}/ 三类结构化目录，后端可插拔；L3 Dream——auto_dream 定时任务对当日 daily 做备份、扫描、用 LLM 蒸馏 / 纠错 / 去重 / 合并进 digest，并输出一份"醒来报告"。另有一条容易被忽略但很关键的纪律：Worker 退役时用 cleanup hook 整体归档或销毁其 workspace 目录，防止残留向量泄漏。
做法
① 记忆分成"当次会话 / 项目长期"两层就够了（不必上三层），当次会话的事实卡片在群任务结束时批量蒸馏一次写入项目层；② 蒸馏动作复用现有 scheduler 的 ticker，做成可关闭的后台任务并给出"蒸馏报告"（这个报告本身就是很好的产品瞬间——让用户看见 Agent 在"整理笔记"，信任感的性价比极高）；③ 补 Worker 退役时的 workspace 归档/清理，与 F10 的变更集抽象共用一套快照机制。
落点
agent/tools/memory.rs、group/worker_pool.rs、scheduler/engine.rs

06交互差距与改进建议

为什么这一章是重点

现有 architecture-adjustment-plan.md 把 14 项调整全部落在后端（引擎 / 上下文 / 权限 / 异步 / A2A / 执行器多态），交互层几乎没有条目。但组织隐喻派产品的共同软肋恰恰是运行期可观测性——用户看不见 Agent 在干什么，就不会信任它，也不会把重要任务交给它。下面 17 项全部是纯前端 + 少量数据支撑，不动架构骨架。其中 D 组三项为 2026-08-03 补录，来自 AgentTeams / AgentSpace 的对照。

A · 让"谁在干什么"一眼可见

P0IX-1 · 席位卡片承载运行态与成本

Relevance AI 的 Workforce 看板把每个 agent 一行，同排展示 Task / 工具图标 / 所用模型 / Eval 通过率 / 平均每任务成本——让"降本"和"降质"在同一屏权衡，这是目前最成熟的呈现方式。

做法：群成员列表的席位卡片从"静态名片"升级为"运行仪表"：当前状态（空闲 / 思考中 / 调工具 ToolName / 等审批 / 失败）、本次任务耗时与 token、历史成功率、累计成本。状态文案要具体到工具名，"正在运行 run_shell"远比"处理中"有信息量。数据来自 F3 的 runs 表。

P0IX-2 · 运行摘要条 + 任务甘特时间线

CrewAI AMP 的 Traces 页可以近乎原样移植：顶部固定一条摘要——total / prompt / completion tokens、请求数、总耗时、预估成本；下方是任务级执行时间线（甘特式），可按任务下钻看 Agent / LLM / 输入 / 输出 / 状态。

做法：群详情加第四个视图 "运行"，与 chat / dispatch / deliverables 并列。甘特图能一眼看出并行度是否真的用上了——如果三个 Worker 的条形是错开的而不是重叠的，说明扇出没生效，这个洞察用聊天流永远看不出来。

P1IX-3 · Work Log 折叠手风琴（每步自评 + 耗时）

Devin 的 planner Work Log 是长任务信息密度最高的呈现：可折叠手风琴，每步带 🟢/🟠/🔴 自评等级 + 时间戳 + 耗时，人能直接跳到出问题的那一步，不用逐条读。

做法：当前 ProcessPanel.tsx 是平铺的工具步骤列表 + shell 输出 <pre>。改为折叠手风琴，每步左侧一个状态点（成功 / 有警告 / 失败），右侧耗时。自评等级可由引擎按 stop_reason + 工具 isError 自动生成，不需要额外 LLM 调用。注意配色须用项目令牌 --status-*-strong，不用 emoji。

P1IX-4 · 气泡来源标签 + 单 Worker 重跑

Coze 在预览区每条回复气泡上带彩色标签标明"由哪个 Agent 回答"，并可点单个 Agent 的运行图标只调它——这是群聊界面里成本最低的可解释性设计。

做法：圆桌消息气泡加席位标签（用席位配色，对标 Claude Code 的 color frontmatter 字段）；气泡右上角 hover 出"重跑此 Worker"。扇出场景下这个按钮价值很大——某个 Worker 答得不好，不用重跑整轮。

B · 让人能随时介入

P0IX-5 · 审批卡片：四按钮 + 参数可编辑 + 超时倒计时

当前审批只有"批准 / 拒绝"。LangGraph Agent Inbox 的契约是四态——accept（原样通过）/ edit（改参数后放行）/ respond（给自由文本反馈让它换个做法）/ ignore（跳过继续），由 config 的四个布尔决定渲染哪几个按钮，描述支持 Markdown。n8n 的 Wait 节点补上了最后一块：Limit Wait Time 超时自动继续。

做法：审批卡片展示工具名 + 参数（可内联编辑）+ 风险等级（由 MCP destructiveHint / readOnlyHint 推导）+ 倒计时进度条。edit 一态在 shell 命令场景价值极高——命令写错了一个路径，改一下就能放行，而不是拒绝后重新组织语言让 Agent 再试一遍。Claude Code 的 PreToolUse hook 用 updatedInput 改写参数后放行，是同一思路的程序化版本。

P1IX-6 · 全局待办收件箱 + 跳回现场

多群 + 定时任务并行时，待审批事项会散落在各处。LangChain 的 Agent Inbox 是 Gmail 式独立收件箱，把所有中断收敛到一个列表，每条支持 "Open in Studio" 跳回执行现场。

做法：侧边栏加"待办"入口带未读角标，聚合三类：待审批工具调用、失败需决策的任务、Worker 主动提问。点击跳转到对应群 + 定位到那条消息。桌面端还有云端做不到的一招：系统通知 + Dock 角标——Agent 后台跑长任务时这是关键体验差异。

P1IX-7 · 从任意消息分叉重跑

LangGraph Studio 把重跑拆成两个语义明确的动作：Edit node state → Fork（改状态后分叉重跑）与 Re-run from here（不改状态、换模型/配置重跑）。

做法：圆桌消息 hover 出这两个动作。OneDesktop 的 build_worker_seed 已经按 seq < broadcast_seq 截取历史，分叉的数据基础天然存在，主要是 UI 与会话 id 派生的工作量。

P2IX-8 · 信息密度滑杆

LangGraph Studio 的线程面板有一根滑杆，拖动即可控制 trace 的展开层级（turn → node → state key），比一堆折叠箭头高效得多。

做法：群聊 / 运行视图顶部加三档切换：只看结论（每 Worker 一条最终回复）/ 看步骤（含工具调用摘要）/ 看全部（含参数与原始输出）。项目已有 SegmentedControl 通用组件可直接复用，符合"先复用再新增"的样式统筹规范。

C · 让结果可比较、可沉淀

P0独有机会IX-9 · 竞速备选方案并排对比

这是全篇性价比最高的一条。broadcast() 竞速时落选方案已经存进了 roundtable_alternatives 表，但前端完全没有暴露——数据已经在库里躺着，只差一个 UI。

而横向看，"多方案并排择优"是竞品的空白区：Cursor 的 best-of-n 未经官方确认，其余产品基本没有。OneDesktop 的竞速语义是差异化资产，却是唯一一个"实现了但用户看不见"的能力。

做法：胜出气泡下方加"查看其他 N 个方案"，展开为并排卡片（各带 Worker 名 / 耗时 / token / 成本），支持"改选此方案"——改选后把该方案回填为后续任务的种子（架构方案 P0-5 层级 3 的"竞速胜者方案回填"正好对接）。

P1IX-10 · 产出物 diff 与变更集审阅

Cursor 2.0 官方把"代码评审"列为 agent 时代的新瓶颈，其 diff 随 agent 工作实时渲染、方向错了随时 Stop 改道。Devin 的 Global Work Diff（任意时间点的全部改动汇总 + 单文件编辑历史 + 跨 shell 的 Command History）是更完整的版本。

做法：当前 GroupDeliverables 只能看不能比。加两件事：① 文件类产出物显示 before/after diff；② 群任务结束时给一个"本次变更集"汇总——改了哪些文件、每个文件谁改的、可一键回滚。并行 Worker 场景下这是安全感的主要来源。

P1IX-11 · 派活前的事前成本预估

Claude Code 文档反复强调结构性成本："每个 teammate 独立上下文，token 随活跃成员数线性增长""broadcast 成本随团队规模成倍增长""调研 / 评审值得，常规任务用单会话更划算"。

做法：成本提示要出现在派活时刻而不只是事后账单。@ 多个 Worker 或点广播时，按钮旁给出"预计 N 次调用 / 约 X tokens / 约 ¥Y"（用历史均值估算）；广播加二次确认。这是把 F3 的记账数据反哺到决策点。

P2IX-12 · DAG 只读拓扑视图

不建议做画布编辑器——OpenAI 弃用 Agent Builder 已经说明纯画布对复杂 Agent 表达力有限，且双向同步是工程地狱。LangGraph Studio 的折中更聪明：定义靠表单/代码，画布只做只读渲染 + 执行态高亮。

做法：GroupDispatch 的 depends_on 复选框保留为录入方式，旁边加一个只读 DAG 图，运行时按状态着色（等待 / 进行中 / 完成 / 失败）。工作量小、信息增益大——依赖关系一旦超过 4 个任务，复选框就完全看不出拓扑了。

P2IX-13 · 启动与长任务的阶段可见化

OpenHands 把会话启动做成显式状态机并对用户可见：WAITING_FOR_SANDBOX → PREPARING_REPOSITORY → RUNNING_SETUP_SCRIPT → SETTING_UP_SKILLS → STARTING_CONVERSATION → READY。桌面端冷启动、群初始化、Worker 首轮加载都适用这个模式。

做法：把"正在加载"这种无信息量的 loading 替换成阶段化进度（正在装配席位 → 注入能力 → 建立会话 → 就绪）。感知性能的提升往往比真实性能优化更划算。

P2IX-14 · 运行回放与分享

Manus 的 replay、Lindy 的任意任务生成公开分享链接，都是把"过程"变成可传播资产。Devin 的 Playbook "Past runs" 标签页则让人能看同事怎么用。

做法：基于 F3 的 runs/run_steps 表导出一次群协作的完整回放（自包含 HTML，与项目 docs/ 下现有 mockup 同构）。桌面端不适合做公开链接，但导出文件分享同样成立，且更符合本地优先的定位。

D · 补录：来自两个新对手的三项 2026-08-03

P1IX-15 · 从单聊平滑升级为群 —— 本轮调研中价值最高的一条交互

阿里在 AgentTeams 的博客里非常清醒地写了一段反向论证："If it's just writing a piece of code, looking up a document, or generating an image, a single chat is a more direct and lower-cost option. The cost of introducing group chats is non-trivial." 只有三类场景值得付这个成本——跨域长时工作流、多 Agent 治理需求、组织级知识沉淀。

OneDesktop 的问题在于：这个成本是在最错误的时刻收取的。当前流程是"先建群 → 想清楚要几个席位 → 各配什么能力 → 才能开始说第一句话"。用户在信息最少的时候被要求做最多的结构性决策，而真实情况几乎总是相反——人是在单聊里聊着聊着，才发现这事一个 Agent 干不完的。

做法：在普通会话的工具条上加一个"升级为协作群"入口。点击后：① 把当前会话的完整上下文作为群的初始共享状态（复用 build_worker_seed）；② 用一次 LLM 调用根据已有对话预填建议席位与任务拆解，用户只需增删改而不是从零填表；③ 原会话降级为群主视角，历史消息原样保留。反向也要能走通：群任务收尾后可"折叠回单聊"，只留结论与产出物。

为什么这条价值最高：它不新增任何后端能力，却直接解决了群协作功能"建了但没人用"的根本原因。竞品做不了这一条——AgentTeams 的 Team 是 K8s CRD，AgentSpace 的工作区是多租户实体，都是重资源，不可能从一次对话里长出来。这恰好是单机形态的结构性优势。

P1IX-16 · 能力体检面板：把"为什么这个席位干不了活"变成可枚举清单

AgentSpace 在权限控制面里专门列了 Diagnostics 维度，枚举四类问题：missing grants（缺授权）/ revoked credentials（凭证已吊销）/ orphaned grants（授权指向已不存在的对象）/ unavailable providers（运行时不可用）。AgentRouter 层面每个 provider 还各有健康预检与错误分类。

这是个被低估的产品设计。多 Agent 系统失败时最典型的用户体验是"它没反应 / 它说它做不了"，而真实原因藏在配置、凭证、网络、版本兼容里。把这些做成一张可枚举、可点击修复的清单，等于把最令人沮丧的黑盒时刻变成一次明确的操作。

做法：扩展页新增"能力体检"，对每个席位输出一行结论：模型可达性（Provider Key 是否有效）· MCP Server 连通性与工具数（F1 落地后）· 外部 CLI 可执行性与版本（F11 的 preflight() 直接喂数据）· 引用的 Skill 是否存在 · workspace 路径是否可写。每条给出"去修复"跳转。建群时也跑一次，把"这个席位当前不可用"前置到配置期，而不是任务跑到一半才炸。

P2IX-17 · 审批快循环与预算触发的审批

AgentSpace 原文："High-impact actions route directly into human approvals, with a fast TabTabTab-style approval loop"，且把触发审批的动作明确分为四类：tool use / document access / external sends / budget-sensitive actions。

两个可直接落的点：

  • 键盘快循环。IX-5 的四态审批卡片如果只能用鼠标点，多 Worker 场景下会变成新的瓶颈——一轮扇出可能连续弹出 5～8 个审批。应支持 Tab 切换焦点 + Enter 批准 + Esc 拒绝的连续操作，以及"本轮全部批准"与"此工具本次会话内不再询问"两个批量出口（后者写入 F3 审计，并在运行摘要条上显示"已授予 N 项临时豁免"作为提醒）。
  • 预算成为审批触发条件。F3 的记账落地后，把"预估成本超过阈值"接进权限判定——单次工具调用预估超过 X、或本次群任务累计超过 Y 时强制转 Ask。这比按工具类型划分危险等级更贴近用户的真实焦虑：多 Agent 最容易失控的不是删文件，是无声地烧钱。

一句话优先级

补录后如果要加第四件：IX-15（单聊升级为群）。前三件解决"能不能用、敢不敢用"，第四件解决"会不会用"——而且它是全表里唯一一条竞品结构上无法跟进的改动。

补录后的战略提醒：三条不要走的岔路
  1. 不要在治理深度上追赶。AgentTeams 有 L1/L2/L3 人类权限层级 + 零信任网关 + 三级凭证标签，AgentSpace 有多租户 + owner/admin/member + OAuth 委托。这些能力的价值前提是"存在一个需要互相防范的组织"。单人场景下它们是纯负担。OneDesktop 只需要做到"我知道 Agent 干了什么、能拦下它"，不需要做到"部门 A 不能看部门 B"。
  2. 不要引入常驻服务依赖。Matrix homeserver、MinIO、PostgreSQL、AI 网关——每一个都会把"双击运行"变成"先读一遍部署文档"。现有的 SQLite + Tauri Event 已经足够支撑单机多 Agent，不要为了对齐对手的架构图而牺牲唯一的独占优势。
  3. 不要把"像个组织"当成目标本身。AgentTeams 把组织隐喻做到了 CRD 级别，但它服务的是真实的企业组织。OneDesktop 的席位是上下文隔离单元（这一点 Manus 的教训已经讲得很清楚），组织隐喻只是让用户容易理解的外壳。当"更像组织"和"更好用"冲突时，选后者——比如不要为了角色完整性去加一个用户根本不会配的"TeamAdmin"层。

09不要做什么

调研中收集到的失败案例与反面教训，比正面经验更值钱。

别做证据启示
不要做可视化画布编辑器 OpenAI 已宣布 Agent Builder 于 2026-11-30 关停（ChatKit 保留）；AutoGen Studio 官方自标"原型工具、非生产就绪"。 画布与代码/配置的双向同步是工程地狱，且对循环、递归、动态成员表达力有限。走 LangGraph 的折中：定义靠表单，画布只做只读渲染 + 执行态高亮（IX-12）。
不要让执行 Agent 自己维护 todo 文件 Manus 实测发现 约 1/3 的动作都花在更新 todo.md 上，纯属 token 浪费，后来改为 planner + executor + knowledge manager 分工。 OneDesktop 的任务状态由 TaskScheduler 系统托管，这个设计是对的，不要退化成让 Worker 自己写计划文件。
不要把子 Agent 当"模仿人类分工" Manus 明确定义子 agent 的目的是隔离上下文而非模仿分工——"LLM 没有人类的认知带宽限制"。 席位设计的依据应是"上下文该不该隔离"，而不是"现实中这活儿归谁"。角色数量不是越多越好。
不要无限增加单 Agent 的可选动作 Copilot Studio 给出经验阈值：可选动作（工具 + topic + agent）超过 30–40 个时表现明显退化。 MCP 打通后工具数会暴涨，必须按席位做工具白名单（对标 Claude Code 的 tools / disallowedTools frontmatter），不能全量注入。
不要让审批只活在会话里 Zapier Agents 被三方实测指出：审批历史只存在会话中、不持久化为审计轨迹。 F2/F3 必须把每次审批决策（含超时自动拒绝）落库，这既是安全需求，也是"自动升级策略"的训练数据。
不要新建 MCP sampling / roots 实现 MCP 2026-07-28 已将 sampling / roots / logging 标记 Deprecated（SEP-2577），建议 sampling 改为直接对接 LLM Provider API。 F1 只实现 tools（核心）+ elicitation（保留且有用），把会话抽象成可丢弃对象为无状态化预留即可。
不要信任 MCP tool annotations 规范原文："clients MUST consider tool annotations to be untrusted unless they come from trusted servers"，且 destructiveHint 默认为 true。 annotations 只能用于降级默认策略（readOnlyHint=true → 默认 Allow），绝不能用于自动提权；未声明按危险处理。
不要照抄 LangGraph 的 interrupt 语义 LangGraph 恢复时整个节点从头重放，interrupt 之前的代码会再跑一遍，副作用必须幂等；官方也不推荐 interrupt_before/after 用于生产 HITL。 OneDesktop 现有的"审批门 + rx.await"是挂起而非重放，本身优于 LangGraph。只抄它的 HumanInterrupt/HumanResponse schema，不抄执行模型。
不要把群协作当默认入口 补录 AgentTeams 官方明确："The cost of introducing group chats is non-trivial"，只有跨域长时工作流 / 多 Agent 治理 / 组织级知识沉淀三类场景值得付这个成本；写段代码、查个文档、生成张图，单聊更直接也更便宜。 群协作是重型工具。正确解法不是降低建群门槛，而是提供从单聊长出群的路径（IX-15）。让用户在信息充分之后再做结构性决策，而不是在第一秒。
不要用消息体在席位间传大内容 补录 AgentTeams 给 MinIO 共享文件系统标注的官方目的就是"降低多智能体 token 消耗"；Manus 的 full/compact 双表示、Lindy 的"可选择传递哪部分上下文"都指向同一件事。 多 Agent 的成本大头是同一份内容被反复塞进 N 个上下文。OneDesktop 单机天然有本地文件系统这个共享底座——席位之间应传文件路径与摘要，让需要的一方自己去读，这比任何压缩策略都有效，且实现成本近乎为零。
不要向外部 CLI 子进程透传凭证环境变量 补录 AgentTeams 的零信任设计把这条讲得很直白："Agents never touch real credentials"，Worker 只拿可吊销 Consumer Token；AgentSpace 的 runtime grants 与 daemon token 也都可单独吊销。 P2-13 落地外部 CLI 执行器时，最容易顺手做、也最难事后补救的就是直接透传 env。子进程的环境变量会出现在进程列表、崩溃转储和它自己的日志里。凭证留主进程、按需代理请求，是单机版能以极低成本获得的等价安全性。
