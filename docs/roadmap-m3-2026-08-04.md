## 2. M2 遗留技术债（M2.5 必收口）

> **2026-08-04 代码复核修正**：本节初稿的诊断部分不准确（数据源自 handoff 日志的二手记录）。以下为 `grep` 实测后的订正版，**并新发现一处 P0 级架构缺口（第 0 条）**。

### 2.0 🔴 P0 新发现：MCP 工具在 Worker 场景完全不可用（R1 × R7 断裂）

- **现象**：`permission::WORKER_DEFAULT_ALLOWED` 仅含 4 个内置工具 `["read_file","write_file","list_dir","get_weather"]`。MCP 工具命名为 `mcp__{server}__{tool}`（见 `ledger.rs::origin_of`），**永远不匹配白名单** → Worker 会话下一律 fail-closed 到 `Deny`。
- **更严重的是**：该常量同时被用作 **`ToolScope` 白名单**，在 3 处调用点过滤工具清单（`group/roundtable.rs:675`、`scheduler/engine.rs:235`、`agent/executor.rs:143`）。这意味着 Worker 回合的 LLM **根本看不见** MCP 工具，连尝试调用都不会发生。
- **影响**：M2 的 R1（MCP 工具打通）与 R7（单聊升级为群）**组合价值归零**。用户接好 MCP、单聊里用得好好的，一升级成群，所有 Worker 立刻失去全部 MCP 能力，且界面上无任何提示——静默降级，比报错更糟。
- **判定**：这不是"待优化"，是 M2 验收口径的漏网。**M2.5 首要任务**，优先级高于去 Tauri 化。
- **修复方向**（详见 `plan-m2.5-2026-08-04.md` T0）：白名单从「工具名字面量清单」升级为「**能力谓词**」——按 `origin` + 副作用等级判定，而非硬编码名字。MCP 工具默认 `Ask`（冒泡审批，A-4 通路已就绪）而非 `Deny`，让人来兜底。

### 2.1 A-1 去 Tauri 化：残留面比记录的小，但泛型污染是主战场

`grep -rn "use tauri::"` 实测（全仓 16 处）：

| 层 | 文件 | 判定 |
|---|---|---|
| 适配层（设计内，**不清**） | `commands/*.rs` ×7、`lib.rs`、`events.rs`、`integration_test.rs` ×2 | ✅ 合法 |
| **端口适配器（设计内，不清）** | `agent/ports.rs` | ✅ 合法 —— `TauriObserver` 按 ADR-001 就该是"唯一知道 Tauri 的适配器" |
| **内核层残留（必清）** | `agent/executor.rs`、`group/roundtable.rs`、`group/scheduler.rs`、`scheduler/engine.rs` | 🔴 **4 个文件** |

- **订正**：不是「内核层 23 处」，是 **4 个文件**。日志把 `<R: Runtime>` 泛型约束混算进了 `use` 语句数。
- **真正的成本在泛型传染**：`<R: Runtime>` / `AppHandle<R>` 全仓 62 处，`group/roundtable.rs` 独占 20 处、`group/scheduler.rs` 12 处。清 4 行 `use` 是假动作，**拆掉泛型传染链才是实际工作量**——这决定了内核能否脱离 Tauri 单测。
- **主战场明确**：`group/roundtable.rs`（998 行，全仓最大文件 + 泛型第一重灾区）。

### 2.2 ADR-001 CI 守卫：载体完全空白

实测：无 `.github/`、无 `.husky/`、`.git/hooks/` 只有 sample、`package.json` 仅 6 个脚本（`dev/build/preview/tauri/test:e2e/test:e2e:update`），**无 lint、无 check、无 test 聚合入口**。

- **决议（已采纳）**：`npm run check` 聚合脚本 + `scripts/check-kernel-purity.sh` + **git `pre-push` hook**（而非 pre-commit）。
- **为什么 pre-push 而非 pre-commit**：单机开发高频小提交，pre-commit 跑 `cargo check` 会把每次提交拖到 30s+，开发者必然 `--no-verify` 绕过，守卫形同虚设。pre-push 频率低、可承受、且拦得住"推上去污染远端"这个真实风险。**代价**：本地可以攒着脏提交，但推送前必须过闸——可接受。

### 2.3 2 个 PRD 阻塞项：代码里已有事实答案，需追认或调整

用户 2026-08-04 决议「现在定」。复核后发现**二者都已在代码里实现**，故性质从「待决策」变为「**追认现状 or 修正**」：

| 阻塞项 | 代码现状 | 建议 |

| Worker 默认 Ask 范围 | `permission.rs:22` 白名单 4 个内置工具；D3′ 的 `Ask→Deny` 降级**已移除**，改为冒泡审批 + 超时 fail-closed 到 `Ignore` | ⚠️ **需修正** —— 白名单机制本身有缺陷（见 §2.0），改为能力谓词 |

### 2.4 审批过载 IX-17（前置到 M2.5）

一轮扇出 5–8 个 Ask 时用户被弹窗淹没。IX-17（键盘快循环 + "本轮全部批准" + "此工具本次会话不再问"）直接决定 M2「敢用」是否成立。

- **与 §2.0 强耦合**：MCP 工具改为默认 `Ask` 后，审批量会**显著上升**（一个 Worker 调 3 个 MCP 工具 × 5 个 Worker = 15 次审批）。**§2.0 和 §2.4 必须同批次交付**，否则修好 MCP 可用性的同时会制造出更严重的弹窗地狱。

## 3. M3 范围与取舍

PRD §3.2 登记的 M3 = `F12 F5 F6 F7 F4 F8 F11 + IX-3/6/7/16`。总口诀：**单机下做 Agent 自组织，但人始终唯一且保中断权**（PRD §8 注）。

### 3.1 M3a · 自组织地基（必做，地基性）

| 需求 | 价值 | 架构决策要点 | 风险 |
|------|------|--------------|------|
| **F7 结构化黑板** | Agent 间共享中间产物/状态，替代"文件传话" | SQLite-backed 黑板表（复用 RunLedger 连接）；读写走事件总线；崩溃可恢复且与 R2 统一观测 | 中（需定义一致性模型） |
| **F5 Worker 间通信** | Worker 能互相发消息/委派子任务 | 新增内核 `MessageBus` 端口（进程内 channel + Tauri Event 上行）；消息体传**文件路径**而非内容体（呼应单机红利） | 低（单进程） |
| **F6 任务心跳防死锁** | 卡死任务可被检测+回收 | 心跳由 executor 周期写状态位；scheduler 超时回收；fail-closed 不丢 run 数据 | 低 |

> **取舍**：F7/F5/F6 是 M3 的"地基三件套"。没有黑板和总线，F12 拓扑策略就是空中楼阁。先做这三件，M3b 才有锚点。

### 3.2 M3b · 策略与声明（依赖 M3a）

| 需求 | 与 M3a 关系 | 取舍 |
|------|-------------|------|
| **F12 通信拓扑策略** | 定义"谁能跟谁说话"，**必须先于 F5 的规模化使用**（PRD §6 硬约束） | 先做声明式策略 schema，再让 MessageBus 路由时求值 |
| **F4 Manifest 导入** | 声明式文件定义群/Agent 拓扑，与 F12 同源 | 与 F12 共用 schema；优先级低于 F12 |
| **F8 Skill 三级预算** | 按 skill 设 token/时间/成本上限，扩展 R2 成本模型 + H1/H2 护栏 | 复用 RunLedger 成本折算；超限自动转审批 |
| **F11 CLI 诊断 / tool approval bridge** | 外部 CLI 席位权限请求与诊断不黑洞 | 复用 R3 ApprovalBroker |
| **IX-3/6/7/16** | 各细分增强 | 视 M3a 落地情况排期 |

### 3.3 明确不做（沿用 §0.2 + NG-S1/2/3）

- 不做 Agent 间"权限层级"（人是唯一裁判）；不引常驻服务（Matrix/PG/MinIO）；不做可视化画布编辑器（NG1）。
- **单机红利复用**：Worker 间冲突只需处理 Agent×Agent，无人×人并发编辑，本地文件锁/黑板版本化即可，无需分布式协调。

## 4. 需要新建的 ADR（M3 关键决策）

- **ADR-009 黑板一致性模型**：最后写入胜出 vs 版本化 CAS。推荐**版本化 CAS**（与竞速 `roundtable_alternatives` 思路一致），崩溃可重放、可观测。
- **ADR-010 MessageBus 端口归属**：✅ **已拍板（2026-08-04）—— 独立端口**。新增第 5 个内核端口 `MessageBus`，不并入 `RunObserver`。
  - **理由**：`RunObserver` 是**单向出向广播**（内核 → UI，无回执、无路由、丢了不影响正确性）；`MessageBus` 是**双向点对点投递**（Worker ↔ Worker，需寻址、需回执、丢了任务就断）。二者的失败语义完全相反——把它们塞进一个 trait，必然出现"这个方法在这个实现里没意义"的空实现，是典型的接口污染。
  - **代价（需承认）**：内核端口从 4 个变 5 个，`engine::run()` 的依赖注入参数再 +1，`RunDeps` 结构体继续膨胀。**缓解**：M2.5 顺手把散装参数收进 `RunDeps`（S0 已做过一轮参数对象化），新增端口只是加字段而非加参数。
- **ADR-011 拓扑策略求值时机**：路由时动态求值（灵活）vs 建群时静态固化（可预测）。推荐**建群时固化 + 运行期可热更**。
- **ADR-012 黑板持久化**：SQLite 表 vs 纯内存。推荐 **SQLite（复用 RunLedger 连接）**——单机红利：崩溃可恢复 + 与 R2 统一观测。

## 5. 排序与里程碑

> **2026-08-04 决议**：✅ **M2.5 先单独收口，验收通过后再开 M3a**（不合并排期）。
> **理由**：M3a 的黑板/总线要挂在内核端口上，若此时内核仍带 `<R: Runtime>` 泛型传染，新端口会被迫跟着染上 Tauri 泛型，等于**在腐化的地基上浇新楼**。先清干净，M3a 的三个新模块才能是纯内核、可单测的。
> **代价**：M3 整体延后约 1 周。**换来的**：M3a 每个模块都能脱离 Tauri 单测，长期回报远大于这一周。

1. **M2.5**（首要收口，详见 `plan-m2.5-2026-08-04.md`）
   - T0 修 MCP × Worker 断裂（§2.0，P0）→ T1 IX-17 审批快循环（与 T0 同批次，防弹窗地狱）→ T2 拆泛型传染链 + 清 4 个内核 `use tauri::` → T3 落 `npm run check` + pre-push 守卫 → T4 成本单价表落 settings。
   - **验收**：Worker 可用 MCP 工具（默认 Ask 冒泡）；5 个 Worker 扇出的审批可在 3 次击键内消化；内核层 `use tauri::` = 0 且 `<R: Runtime>` 不出现在 `group/`、`scheduler/`、`agent/executor.rs`；`npm run check` 一键跑通并被 pre-push 拦截；换 provider 后成本显示正确。
2. **M3a**：F7 黑板 → F5 总线（接 F12 雏形）→ F6 心跳。
   - 验收：两个 Worker 通过黑板交换中间结果完成任务；卡死任务被回收；无僵尸任务残留。
3. **M3b**：F12 → F4 → F8 → F11 → IX-*。
   - 验收：声明式 Manifest 建群；skill 超预算自动转审批；CLI 席位诊断可见。

## 7. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 自组织易失控 | 人始终保中断权（任意时刻暂停/解散群）；拓扑策略默认**最小权限**（Worker 默认不可互访，需显式授权） |
| 黑板变新瓶颈 | 读写走事件总线 + 批量刷盘；不做强事务 |
| 单机单人下 M3 价值难验证 | dogfooding 样本 + 内置"自组织演示群"（预置拓扑）做验收 |
| M3 与 M2 一样「骨架立血肉未填」 | M3a 每件都配一个端到端 dogfooding 场景，不做无消费方的抽象 |
