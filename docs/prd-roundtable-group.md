## 1. 问题陈述（Problem Statement）

当前 OneDesktop 的 Agent 是「单实例、单会话」模式：一个需求只能由一个 Agent 顺序处理。当用户面对**需要多个专长 Agent 并行协作**的复杂任务（如「调研 + 写稿 + 做图」「前后端联调」）时，只能靠人在多个会话间手动搬运上下文。

现有「群主模式」虽允许一个群主 Agent 拆解并 `@` 多个成员，但存在三处硬伤：

1. **Worker 仅是 role 标签**：无状态、无能力画像、无并发控制，群主无法掌握「谁在忙、谁能接」。
2. **派活靠自然语言 `@` 多人**：并行度受群主 LLM 一轮输出限制；`depends_on` 字段写了却无人消费，依赖任务被迫串行。
3. **无自动验收闭环**：子任务全跑完不会触发群主验收，经常「跑完没人管」。

**代价**：复杂任务端到端时延高、群主成瓶颈、执行过程不可审计、失败无统一问责。

> 证据：基于对《Agent 群协作系统-技术架构文档》《Agent 群协作系统-需求文档》的现状分析；方案已通过头脑风暴阶段锁定（设计记录见项目记忆）。

## 2. 目标（Goals）

**用户目标**
- **G1** 用户能在圆桌里把一个复杂任务拆给多个 Worker **真正并行**执行，并实时看到各自进度。
- **G2** 群主（人类或 Agent）只做「拆解 + 验收」判断，不必亲自干技术活、不必逐轮 `@`。
- **G3** 任何一轮任务都有明确出口——完成即验收沉淀，失败即重试/换人/上报，**绝不悬空**。

**业务目标**
- **G4** 复杂任务端到端交付时延较「群主逐轮串行 `@`」下降 **≥50%**。
- **G5** 群主 LLM 的 token / 延迟消耗下降（确定性调度接管 fan-out 与 join）。
- **G6** 资源泄漏事件 **= 0**（群解散后无 worker 残留、无工作空间串台）。

---

## 3. 非目标（Non-Goals）

- **NG1** 不做跨群编排 / 群间任务流转（属文档 Phase 4，独立立项）。
- **NG2** 不做 Agent 自我繁殖或运行时动态创建新 Agent（文档明确不支持，且治理风险高）。
- **NG3** 不做平权模式的群（v1 仅群主模式，规划/执行分离是核心治理假设）。
- **NG4** 不做独立「任务详情页」应用（执行以可折叠卡片内嵌圆桌，避免上下文割裂）。
- **NG5** 不做多人类实时协同编辑（v1 单人类操盘，群内人类仅一人）。
- **NG6** 不做群间共享工作空间（每群独立隔离，见 §4/§5）。

> 理由：均超出 v1 范围或与前序约束冲突；v1 聚焦「治理优先的可审计并行协作」。

## 4. 核心概念（Concept Definitions）

| 概念 | 定义 |
|------|------|
| **圆桌 / 群（Group）** | 多个 Agent 协作的聊天空间，承载讨论与执行。 |
| **群主（Owner）** | 群内负责拆解需求、验收产出的规划型 Agent（LLM），由人类任命。 |
| **Worker** | 被指派执行子任务的 Agent **运行时实体（一等公民）**，带状态机与能力画像。 |
| **席位（Seat）** | Worker 的执行者身份，三种模型：静态（建群定死）/ 动态（群主运行时可调）/ 能力（按能力标签临时匹配）。 |
| **工作空间（Workspace）** | 每个圆桌在本地 `~/.one-desktop/groups/{id}/` 的独立目录，含 per-worker 沙箱。 |
| **任务闭环（Task Cycle）** | `Received → Decomposed → Executing → Reviewing → Accepted` 的单轮需求生命周期。 |
| **群生命周期** | `Draft → Active ↔ Paused → Archiving → Archived`。 |

## 5. 用户故事（User Stories）

### P0（Must-Have）
- **US1** 作为**人类操盘者**，我想从侧边栏一键创建群并指定群主与初始 Worker 席位，以便快速拉起一个协作空间。
- **US2** 作为**人类操盘者**，我想在圆桌里发一条需求，由群主自动拆解并派给多个 Worker 并行执行，以便我不必手动 `@` 每个人。
- **US3** 作为**人类操盘者**，我想在圆桌里实时看到每个 Worker 的状态（Idle/Busy/Offline）与各自执行进度卡片，以便掌握全局。
- **US4** 作为**群主 Agent**，我想把需求拆成带依赖关系的子任务并交给调度器并行派发，以便我专注拆解与验收而非调度细节。
- **US5** 作为**Worker Agent**，我想在被派活时拿到独立的工作目录与明确输入，以便我安全读写文件而不影响其他 Worker。
- **US6** 作为**人类操盘者**，我想在子任务全部完成后收到群主验收结论并确认产物已沉淀，以便闭环不悬空。
- **US7** 作为**人类操盘者**，我想在任意时刻暂停/恢复/解散群，且解散后无 worker 残留、工作空间可查，以便我完全掌控生命周期。

### P1（Should-Have）
- **US8** 作为**人类操盘者**，我想在运行时给群动态加人/换人（动态席位），以便应对能力不足或失败。
- **US9** 作为**人类操盘者**，我想对 Worker 的工具调用做人工批准（HITL），以便高风险操作可控。
- **US10** 作为**人类操盘者**，我想在群解散后从归档里浏览聊天记录与产物，并可在 Finder 打开工作空间。

### P2（Future）
- **US11** 作为**系统**，我想在 Worker 连续失败时自动上报人类，以便严重问题不沉默。
- **US12** 作为**未来扩展**，工作空间与调度结构应支持后续跨群编排而不必重构。

## 6. 功能需求（Requirements）

### P0 · Must-Have

**FR-1 群创建（Draft → Active）**
- 人类在侧边栏「群」区点「创建群」，填写群名、目标、选群主、配置初始席位（静态名单 / 动态候选池 / 能力标签库）。
- 确认前**不创建任何 worker session、不建工作空间**；取消即销毁无残留。
- *验收*：Given 人类填完表单点确认，When 提交，Then 群进入 Active、Worker 席位就位（Idle）、圆桌开启、工作空间目录已建。

**FR-2 圆桌聊天 + 内嵌执行卡片**
- 圆桌为「讨论气泡 + 内嵌执行卡片（可折叠）」混合模型；侧边成员栏展示 Worker 与状态点。
- *验收*：Given 某 Worker 在执行，When 它流式回报，Then 圆桌出现可折叠执行卡片（进度/依赖/产出），不脱离上下文且可折起压低噪音。

**FR-3 群主拆解 + 结构化派活（混合编排）**
- 人类发需求 → 群主 LLM 拆解 → 生成 `SubTask[]`（含 worker / `depends_on` / 产出要求 / 席位策略）→ 调度器消费并 fan-out。
- *验收*：Given 群主产出 SubTask[]，When 调度器 tick，Then 无依赖子任务全部 `InProgress` 并发执行，有依赖的等依赖 `Completed` 后进入下一批。

**FR-4 真并行执行 + 工作空间隔离**
- 每个 Worker = 一个 session（`grp:{gid}:{wid}`），复用现有引擎；其 filesystem 工具 base 沙箱到 `groups/{id}/workers/{wid}/`。
- *验收*：Given 两个 Worker 并行，When 各自写文件，Then 文件落在各自 subdir，且 `sanitize_path` 拦截越界写入。

**FR-5 任务闭环 + 自动验收触发**
- batch 全部 `Completed` → 系统消息 `@群主` → 群主 LLM 验收 → 人类确认 → 产物沉淀 `artifacts/`。
- *验收*：Given 一批子任务全 `Completed`，When 触发，Then 群主收到验收消息且必须产出 accept/reject；reject 回 Decomposed；accept 产物落盘。

**FR-6 分级问责 / 失败处理**
- 瞬时失败自动重试 ≤ N 次；结构性失败（能力不匹配/越权）立即上报群主；连续 2 次失败上报人类。
- *验收*：Given Worker 瞬时失败，When 重试 ≤ N 成功，Then 继续；Given 连续 2 次失败，When 发生，Then 上报人类且群不卡死。

**FR-7 群生命周期管理 + 资源清理**
- Paused/恢复；Archiving 强制 cancel 所有 worker session + release pool + 工作空间置只读；Archived 只读可查。
- *验收*：Given 群进入 Archiving，When 执行，Then 所有 worker session 被 cancel，无残留进程，工作空间只读。

### P1 · Should-Have
- **FR-8 动态席位管理**：群主运行时加人/换人，WorkerPool 同步。
- **FR-9 群内 HITL**：worker 工具调用 `ApprovalRequest` 带 `session_id`，圆桌针对该 worker 卡片给批准/拒绝，复用核心 `approve_tool`。
- **FR-10 归档浏览**：Archived 群可查看聊天 + 产物，UI 提供「在 Finder 打开」。

### P2 · Future
- **FR-11 连续失败自动上报**（同 US11）。
- **FR-12 跨群就绪**：数据面与调度结构预留跨群接口（不实现）。

## 7. 成功指标（Success Metrics）

**北极星**：多 Agent 协作任务的端到端**验收通过率**（按时验收且无悬空、无泄漏）。

**驱动指标**
- 并行度：同时运行 Worker 数（目标 ≥ 建群 Worker 数的 80%）。
- 拆解 → 首个 Worker 启动时延（目标 < 群主一轮 LLM 时延）。
- fan-out 吞吐：单批子任务数。

**健康指标**
- Worker 失败率 / 重试率（警戒线 < 20%）。
- 群主 LLM token 消耗（较纯聊天驱动下降 ≥30%）。
- 资源泄漏次数（硬指标 = 0）。
- 验收闭环率（= 100%，无悬空 batch）。

**衡量方式**：OneDesktop Metrics（AtomicU64）+ 群事件日志；评估窗口：上线后 1 周 / 1 月。

## 8. 依赖与约束（Dependencies & Constraints）

- 复用现有 `AgentLoopEngine::run`（session 寻址）、`agent-event`（带 `session_id`）、`send_message / approve_tool / cancel_agent` 命令、前端 `useAgent` 事件过滤——**核心零侵入**。
- 数据根 `~/.one-desktop`（paths.rs 已统一）；群工作空间 `groups/{id}/`。
- 文档约束：不支持 Agent 创建新 Agent；仅群主模式。
- LLM 并发：N worker 并行 = N 路 API 调用，需 429 退避 + `max_concurrency` 封顶。

---

## 9. 风险与缓解（Risks）

| 风险 | 缓解 |
|------|------|
| R1 群主 LLM 拆解质量不稳 | SubTask 结构化校验 + 人类可打回重做 |
| R2 并行多 worker 事件扇入致 UI 抖动 | 列表虚拟化 + 按 `session_id` 对账 |
| R3 工作空间膨胀 | Archiving 置只读，删除需人类确认；可加配额（P2） |
| R4 群主失控 / 私自解散 | 群主仅拆解+验收；解散须人类二次确认 |
